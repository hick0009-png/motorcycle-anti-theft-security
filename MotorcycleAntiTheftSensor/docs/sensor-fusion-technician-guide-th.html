Motorcycle Anti-Theft Sensor — Sensor Fusion Technician Guide v1.0

1. วัตถุประสงค์ของคู่มือ

คู่มือนี้อธิบายการทำงานของระบบตรวจจับเสียงร่วมกับเซนเซอร์อื่น โดยมีเป้าหมายให้ไมโครโฟนช่วยตรวจพฤติกรรมที่เกี่ยวข้องกับการโจรกรรม เช่น การทุบ การงัด การใช้สว่าน การทำลายชิ้นส่วน และการสตาร์ตหรือเคลื่อนย้ายรถ

ขอบเขตสำคัญ: เอกสารนี้เป็นคู่มือของแบบระบบที่ได้รับอนุมัติ ไม่ใช่หลักฐานว่า APK ที่ติดตั้งอยู่ในปัจจุบันมีความสามารถทั้งหมดนี้แล้ว ช่างต้องตรวจหมายเลขรุ่นและผล Acceptance Test ก่อนระบุว่าระบบพร้อมใช้งานจริง

ระบบไม่ใช้ไมโครโฟนเพื่อดักฟัง ไม่ถอดคำพูด และไม่บันทึกคลิปเสียง การวิเคราะห์ทั้งหมดเกิดบนโทรศัพท์ ข้อมูลดิบอยู่ใน RAM ชั่วคราวประมาณ 1–2 วินาทีและถูกเขียนทับอย่างต่อเนื่อง

2. หลักการทำงานโดยสรุป

AudioRecord — รับเสียง Mono 16 kHz
↓
Audio Signal Gate — ตรวจความเปลี่ยนแปลงและเสียงกระแทก
↓
YAMNet — จำแนกประเภทเสียงเฉพาะเมื่อ Signal Gate เปิด
↓
Audio Threat Candidate — เก็บ Metadata ใน RAM 15 วินาที
↓
Sensor Fusion — รอเซนเซอร์อื่นยืนยัน
↓
Incident Engine — เปิดเหตุการณ์และส่ง Telegram
กฎหลัก: เสียงเพียงอย่างเดียวไม่ส่ง Telegram ต้องมี Vibration, Power หรือ Location ยืนยันภายในช่วงเวลาเดียวกันก่อน ส่วน Light เป็นหลักฐานประกอบและไม่ยืนยันเพียงลำพัง

3. ระบบรู้และไม่รู้อะไรจากเสียง

ระบบรู้ระบบไม่รู้
ประเภทเสียงโดยประมาณ เช่น กระแทก สว่าน เครื่องยนต์ตัวตนของผู้ทำให้เกิดเสียง
คะแนนความมั่นใจของโมเดลเจตนาว่าเป็นเจ้าของรถหรือผู้โจรกรรม
ระดับเสียงเทียบกับเสียงพื้นฐานระดับเดซิเบลจริง เพราะไมโครโฟนโทรศัพท์ไม่ได้สอบเทียบ
เวลาที่เริ่มตรวจพบและจำนวนครั้งข้อความสนทนาหรือคำพูดของบุคคล

กลุ่มเสียงที่ใช้

IMPACT
Knock, Bang, Thump, Whack
BREAKING
Smash, Crash, Breaking, Shatter
POWER_TOOL
Drill, Power tool, Sawing
ENGINE_ACTIVITY
Motorcycle, Engine starting, Idling, Revving
METAL_TAMPER
Scrape, Clang, Keys jangling
เสียงที่ละเว้น
เสียงพูด เพลง สุนัข ลม ฝน และเสียงทั่วไป

4. สถานะการทำงาน

สถานะไมโครโฟนทำอะไรอนุญาตให้แจ้งเตือนหรือไม่
Disarmedหยุด AudioRecord และล้าง Candidateไม่อนุญาต
Arming / Calibratingเก็บเสียงพื้นฐานประมาณ 10 วินาทีและตรวจสุขภาพไมค์ไม่อนุญาต
Armedเปิด Signal Gate และจำแนกเสียงเมื่อจำเป็นอนุญาตเมื่อ Sensor Fusion ยืนยัน
Alert Activeเก็บหลักฐานเสียงเพิ่มในเหตุการณ์เดิมส่งเพิ่มเฉพาะเมื่อระดับความรุนแรงสูงขึ้น
Audio Degradedเซนเซอร์อื่นทำงานต่อ แต่ไมค์ไม่ถูกใช้ตัดสินรายงานสถานะเสื่อมผ่าน UI และ /status

เสียงในช่วง Calibrating ต้องไม่สร้าง Candidate เพราะเจ้าของรถอาจกำลังกด Arm จัดวางโทรศัพท์ หรือเดินออกจากรถ หลังเข้าสู่ Armed แล้วจึงเริ่มตรวจพฤติกรรมเสี่ยง

6. ความแข็งแรงของหลักฐาน

หลักฐานยืนยันที่แข็งแรง

  • Vibration: แรงสั่นสะเทือนของโทรศัพท์หรือรถผิดปกติ
  • Location: รถเคลื่อนจากจุด Arm มากกว่าค่าคลาดเคลื่อนที่ยอมรับได้
  • Power: สายชาร์จถูกถอดขณะระบบ Armed

หลักฐานประกอบ

  • Light: แสงเปลี่ยน เช่น มีการเปิดเบาะหรือพื้นที่ปิด
  • Audio: เสียงต้องสงสัยจาก YAMNet
  • Location ขนาดเล็ก: การเปลี่ยนตำแหน่งที่ยังอยู่ในช่วงความคลาดเคลื่อน GPS
ห้าม: ใช้ Light เพียงตัวเดียว หรือใช้คะแนนเสียงเพียงตัวเดียวเปิด Incident จริง

การจับคู่เวลา

ระบบจับคู่หลักฐานได้ทั้งสองทิศทาง โดยใช้เวลาชนิด Monotonic/Elapsed time:

  • เสียงเกิดก่อน แล้ว Vibration ตามมาภายใน 15 วินาที
  • Vibration เกิดก่อน แล้วเสียงตามมาภายใน 15 วินาที

ห้ามใช้เวลาจากนาฬิกาหน้าจอเพียงอย่างเดียว เพราะผู้ใช้อาจปรับเวลาเครื่องหรือเวลาอาจเปลี่ยนจากเครือข่าย

กฎตามลักษณะเสียง

ชนิดเงื่อนไขเสียงเบื้องต้นเหตุผล
เสียงสั้น: Impact/Breakingยอมรับหนึ่งหน้าต่างเมื่อ DSP พบ onset จริง และความมั่นใจเริ่มต้นประมาณ 70%เสียงกระแทกอาจสั้นมาก
เสียงต่อเนื่อง: Power tool/Engineพบอย่างน้อย 2 หน้าต่าง รวมประมาณ 1.5–2 วินาที ความมั่นใจเฉลี่ยเริ่มต้นประมาณ 65%ลดการเข้าใจเสียงสั้นผิดเป็นสว่านหรือเครื่องยนต์
ค่า 70% และ 65% เป็นค่าเริ่มต้นสำหรับ Pilot เท่านั้น ต้องปรับจากผลทดสอบบน Huawei และเสียงหน้างานจริงก่อนล็อกเป็นค่า Production

8. การแจ้ง Telegram

ไมค์ตรวจพบ Candidate เพียงอย่างเดียวจะไม่ส่งข้อความ เมื่อ Sensor Fusion ยืนยันแล้ว ข้อความต้องบอกเหตุผลอย่างตรงไปตรงมา ไม่กล่าวยืนยันว่าเป็นโจร แต่ใช้คำว่า “ตรวจพบความเสี่ยง” หรือ “อาจกำลังถูกเคลื่อนย้าย”

ตัวอย่าง: เครื่องมือไฟฟ้าและแรงสั่น

🚨 รถอาจกำลังถูกสตาร์ตหรือเคลื่อนย้าย เสียงที่ตรวจพบ: เครื่องยนต์กำลังสตาร์ต ความมั่นใจของเสียง: 87% เซนเซอร์ยืนยัน: • ตรวจพบแรงสั่นแบบเครื่องยนต์ • ตำแหน่งรถเปลี่ยนจากจุดที่ Arm • เคลื่อนที่ประมาณ 22 เมตร เวลา: 14:35:07 📍 เริ่มติดตามตำแหน่งรถแบบสดแล้ว

กติกาป้องกันสแปม

  1. ส่งครั้งแรกเมื่อเหตุการณ์ได้รับการยืนยัน
  2. ส่งอัปเดตเฉพาะเมื่อระดับสูงขึ้น เช่น Warning เป็น Critical หรือเริ่มเคลื่อนที่
  3. เสียงประเภทเดิมที่เกิดซ้ำให้รวมจำนวนใน Incident เดิม
  4. เริ่ม Live Location เฉพาะเมื่อเข้าเงื่อนไขการเคลื่อนย้ายจริง
  5. ส่งข้อความปิดเหตุการณ์เมื่อ Disarm หรือระบบปิดเหตุการณ์ตามกฎ

9. ข้อมูลที่ไม่ถูกส่งหรือบันทึก

  • ไม่มีไฟล์ WAV, PCM, MP3 หรือคลิปเสียง
  • ไม่มีการถอดคำพูด
  • ไม่มีบทสนทนาของบุคคล
  • ไม่มีเสียงดิบใน Log หรือฐานข้อมูล
  • ไม่มีการส่งผลจำแนกทุกครั้งไป Telegram
  • Candidate ที่ไม่ได้รับการยืนยันจะไม่เป็น Event ถาวร

10. ขั้นตอนทดสอบหน้างาน

10.1 เตรียมระบบ

  1. ตรวจว่าโทรศัพท์อนุญาตสิทธิ์ไมโครโฟนและตำแหน่ง
  2. ตรวจว่า Telegram จับคู่กับบัญชีเจ้าของแล้ว
  3. วางโทรศัพท์ในตำแหน่งติดตั้งจริงและเสียบสายชาร์จ
  4. กด Arm และรักษาสภาพแวดล้อมให้เป็นปกติระหว่าง Calibrating 10 วินาที
  5. ตรวจ UI ว่า Microphone แสดง Listening/Healthy และ Last sample เปลี่ยน

10.2 ทดสอบเสียงอย่างเดียว — ต้องไม่แจ้ง

  1. เปิดเสียงรถหรือเสียงสว่านจากโทรศัพท์อีกเครื่อง โดยไม่แตะรถ
  2. ตรวจว่า UI อาจแสดง Candidate ชั่วคราว
  3. รอเกิน 15 วินาที
  4. ยืนยันว่าไม่มี Telegram และไม่มี Incident ถาวร

10.3 ทดสอบ Impact + Vibration

  1. สร้างเสียงเคาะที่ปลอดภัยพร้อมเขย่าหรือทำให้รถสั่นตามขั้นตอนทดสอบ
  2. ยืนยันว่าเหตุการณ์ทั้งสองเกิดห่างกันไม่เกิน 15 วินาที
  3. คาดหวัง Warning หนึ่งข้อความ พร้อมประเภทเสียงและ Vibration
  4. ทำซ้ำหลายครั้งและยืนยันว่าไม่ส่งข้อความใหม่ทุกครั้ง

10.4 ทดสอบ Power tool + Vibration

  1. ใช้ไฟล์เสียงหรือเครื่องมือจำลองที่ปลอดภัย ไม่สัมผัสชิ้นส่วนรถ
  2. สร้างแรงสั่นร่วมอย่างควบคุม
  3. คาดหวัง Critical พร้อมคำอธิบายว่าเป็นเครื่องมือไฟฟ้า/สว่าน

10.5 ทดสอบ Engine + Movement

  1. ทำในพื้นที่ควบคุมและมีผู้ดูแลรถ
  2. ตรวจ Engine activity ร่วมกับ Vibration
  3. เคลื่อนรถเกินระยะและความแม่นยำที่นโยบาย GPS กำหนด
  4. คาดหวัง Critical และเริ่ม Telegram Live Location

10.6 ทดสอบการล้างข้อมูล

  1. สร้าง Audio Candidate โดยไม่ยืนยัน แล้วกด Disarm
  2. Arm ใหม่และสร้าง Vibration ภายใน 15 วินาที
  3. ต้องไม่จับคู่ Vibration รอบใหม่กับเสียงจากรอบก่อน

11. การจัดการความผิดปกติ

อาการพฤติกรรมที่ถูกต้องสิ่งที่ช่างตรวจ
ไม่มีสิทธิ์ไมค์แสดง Microphone unavailable; เซนเซอร์อื่นทำงานต่อAndroid Permission และ AppOps
AudioRecord เปิดไม่ได้ลองใหม่แบบจำกัดจำนวน แล้วเปลี่ยนเป็น Failed/Degradedแอปอื่นกำลังใช้ไมค์หรือไม่ และ Log ที่ไม่เปิดเผยเสียง
โมเดลโหลดไม่ได้ปิด Audio classification แต่ไม่ทำให้ Service ล่มไฟล์โมเดล เวอร์ชัน และ checksum
ประมวลผลไม่ทันทิ้งเฟรมเก่า ไม่บล็อก AudioRecord หรือ Main ThreadInference latency และจำนวน dropped frames
GPS ยังไม่มี fixส่งเหตุการณ์ที่ยืนยันแล้วโดยไม่รอที่อยู่Location permission, accuracy และอายุ fix
คะแนนเสียงต่ำทิ้งผล ไม่สร้าง Candidateสภาพเสียงจริงและค่าความมั่นใจ
Candidate หมดอายุลบจาก RAM โดยไม่สร้าง Eventนาฬิกา elapsed time และ session ID
ห้ามระบบทำงานแบบเงียบ: ถ้า AudioRecord หรือโมเดลล้มเหลว UI และคำสั่ง /status ต้องระบุว่า Audio classification ใช้งานไม่ได้ ห้ามคงสถานะ Healthy จากข้อมูลเก่า

12. Checklist ตรวจรับ

  • ไมค์เริ่มหลัง Arm และหยุดหลัง Disarm
  • ช่วง Calibrating 10 วินาทีไม่สร้างเหตุการณ์
  • UI แสดง Listening, Last sample และสถานะโมเดลอย่างตรงไปตรงมา
  • เสียงอย่างเดียวไม่ส่ง Telegram
  • เสียงรถคันอื่นโดยไม่มีแรงสั่นหรือการเคลื่อนที่ไม่แจ้ง
  • Impact + Vibration เปิด Warning
  • Power tool + Vibration เปิด Critical
  • Engine + Movement เปิด Critical และ Live Location
  • Candidate จับคู่ได้ทั้งเสียงก่อนและเซนเซอร์ก่อน
  • Candidate หมดอายุภายใน 15 วินาที
  • Disarm/Arm รอบใหม่ไม่ใช้ Candidate เก่า
  • ข้อความ Telegram แสดงประเภทเสียง คะแนน และเซนเซอร์ยืนยัน
  • เหตุการณ์ซ้ำถูกรวมและไม่สแปม
  • ไม่มีไฟล์เสียงหรือ PCM ดิบใน Storage, Database และ Log
  • Audio failure ไม่ทำให้เซนเซอร์อื่นหรือ Service หยุด
  • ผ่านการทดสอบจริงบน Huawei และโทรศัพท์ Telegram อีกเครื่อง

13. ค่าตั้งต้นสำหรับ Pilot

รายการค่าเริ่มต้นหมายเหตุ
Audio sample rate16 kHz Mono PCM16ตรงกับอินพุต YAMNet
Calibration10 วินาทีไม่สร้าง Candidate
Correlation window15 วินาทีจับคู่ได้สองทิศทาง
Candidate capacityสูงสุด 8 รายการรวมประเภทซ้ำ
Transient PCMประมาณ 1–2 วินาทีใน RAMเขียนทับและไม่ลง Storage
Impact confidenceเริ่มประมาณ 70%ต้องมี DSP onset และเซนเซอร์ยืนยัน
Sustained confidenceเฉลี่ยเริ่มประมาณ 65%อย่างน้อย 2 หน้าต่าง

ค่าทั้งหมดต้องปรับจากข้อมูลทดสอบจริง ห้ามลด Threshold เพื่อทำให้ Demo ผ่านโดยไม่มีการวัด False positive และ False negative

14. สรุปสำหรับช่าง

จำกฎเดียวให้ได้: ไมโครโฟนเสนอว่า “อาจมีอะไรผิดปกติ” แต่เซนเซอร์ของตัวรถต้องยืนยันก่อนระบบกล่าวว่าเป็นเหตุการณ์และส่ง Telegram

เมื่อพบปัญหา ให้ตรวจตามลำดับ: Armed หรือไม่ → ไมค์ Listening หรือไม่ → โมเดล Ready หรือไม่ → มี Candidate หรือไม่ → มีเซนเซอร์ยืนยันภายใน 15 วินาทีหรือไม่ → Incident ถูกสร้างหรือไม่ → Telegram ส่งสำเร็จหรือไม่
