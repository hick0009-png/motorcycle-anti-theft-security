# ภาค A — รองรับเครื่องที่ไม่มีเซ็นเซอร์

## A1. ข่าวดี: ชั้นข้อมูลพร้อมแล้ว ขาดแค่ทางขึ้นมาถึงหน้าจอ

เก็บครบอยู่แล้วทุก source: `isAvailable`, `vendor`, `powerMa`, `resolution`,
`minDelayUs`, `reportingMode`, `isWakeUp` — อ่านจาก `getDefaultSensor()` จริงบนเครื่องนั้น
มี `SensorScanner` อีกตัวทำงานซ้ำกันสำหรับหน้าแดชบอร์ด

**ปัญหาคือไม่มีอะไรส่งค่าพวกนี้ขึ้นไปถึงหน้าตั้งค่า** `SensorSourceUiModel.isAvailable`

## A2. สามสถานะที่ต้องแยกให้ชัด (อย่ายุบเหลือสองสถานะ)

| สัญลักษณ์ | สถานะ | ความหมาย | สิ่งที่ทำได้ |
|---|---|---|---|
| 🟢 | **มีและใช้ได้** | `isAvailable = true` และสุขภาพปกติ | ตั้งได้ทุกบทบาท |
| 🟡 | **มีแต่จำกัด** | มีฮาร์ดแวร์ แต่ `minDelayUs` ช้ามาก / เป็น on-change / ยังไม่ได้สิทธิ์ / ยังไม่ปรับเทียบ | ตั้งได้ แต่ต้องบอกข้อจำกัด |
| ⚪ | **ไม่มีในเครื่องนี้** | `isAvailable = false` | ตั้ง "หลัก" ไม่ได้ (จะถูกปฏิเสธทั้งชุด) |

## A4. กฎการตัดสินใจเมื่อเซ็นเซอร์หาย — ต้องเป็นนโยบายในโดเมน ไม่ใช่ if ใน Compose

```kotlin
sealed interface ProfileDeviceSupport {
    data object Supported : ProfileDeviceSupport

    data class Unsupported(val missing: Set<SensorSource>, val reasonTh: String) : ProfileDeviceSupport

```

เกณฑ์ที่เสนอ ต่อโหมด:

| โหมด | ขาดอะไรแล้ว **ใช้ไม่ได้** | ขาดอะไรแล้ว **จำกัด** |
|---|---|---|

**สำคัญ:** ต้องบล็อกที่ "ตอนเลือกโหมด" และ "ตอน Arm" ทั้งสองจุด
ไม่ใช่ปล่อยให้กด Arm ผ่านแล้วเงียบ

# ภาค B — วิเคราะห์โหมดเฝ้าประตู

## B1. ความเข้าใจของเจ้าของถูกต้องในเชิงฟิสิกส์

ประตูหมุนรอบแกนบานพับที่**ตั้งฉากกับพื้น** การเปลี่ยนแปลงจึงเป็น **yaw (การหันทิศ) เกือบล้วน ๆ**

ผลที่ตามมาซึ่งสำคัญมาก: **แรงโน้มถ่วงไม่เปลี่ยนเลยเมื่อหมุนรอบแกนตั้ง**
แปลว่า **มาตรวัดความเร่งมองไม่เห็นการเปิดประตูโดยหลักการ** ไม่ว่าจะตั้งความไวเท่าไร
เซ็นเซอร์ที่ "เห็น" ประตูเปิดได้จริงมีเพียงสองตัว:

- **ไจโรสโคป** — วัดอัตราการหมุน แล้วอินทิเกรตเป็นมุม แม่นในระยะสั้น ไม่มีจุดอ้างอิงสัมบูรณ์
- **เข็มทิศ (แมกนีโตมิเตอร์)** — วัดทิศสัมบูรณ์ ไม่สะสมความคลาดเคลื่อน แต่โดนโลหะรบกวน

การที่เจ้าของนึกถึงเข็มทิศจึงถูกทาง และตอบโจทย์จุดอ่อนที่โค้ดปัจจุบันมีอยู่จริง

## B2. แต่โค้ดปัจจุบันไม่ได้ใช้เข็มทิศ

[AndroidProtectionRuntime.kt:1186](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/protection/AndroidProtectionRuntime.kt)

```kotlin
val sensor = manager.getDefaultSensor(Sensor.TYPE_GAME_ROTATION_VECTOR)
    ?: manager.getDefaultSensor(Sensor.TYPE_ROTATION_VECTOR)
    ?: return
```

- **GAME_ROTATION_VECTOR** = gyro + accel **ไม่มีเข็มทิศ** → ไม่มีจุดอ้างอิง yaw สัมบูรณ์
- **ROTATION_VECTOR** (ตัวสำรอง) = gyro + accel + เข็มทิศ → มีจุดอ้างอิง
- **GEOMAGNETIC_ROTATION_VECTOR** (accel + เข็มทิศ ไม่ต้องมี gyro) — **ไม่ถูกเรียกใช้เลย**

## B3. ข้อบกพร่องที่พบจากการอ่านโค้ด (เรียงตามความร้ายแรง)

### B3-1 · เครื่องไม่มี gyro = โหมดประตูตายเงียบ 🔴

`?: return` ที่บรรทัด 1188 — ถ้าไม่มีทั้งสองตัว **listener ไม่ถูกลงทะเบียน แล้วจบ**
ไม่มี exception ไม่มี log ไม่มีการแจ้งผู้ใช้ แอปยัง Arm สำเร็จ ขึ้นสถานะ "กำลังป้องกัน" ตามปกติ
**แต่จะไม่มีวันตรวจพบประตูเปิด**

เครื่องราคาประหยัดที่ไม่มี gyro ยังมีขายอยู่จริงในตลาดไทย และทั้ง GAME_ROTATION_VECTOR
กับ ROTATION_VECTOR ส่วนใหญ่ต้องพึ่ง gyro — ตัวที่ออกแบบมาสำหรับเครื่องไม่มี gyro คือ
GEOMAGNETIC_ROTATION_VECTOR ซึ่งโค้ดไม่ได้เรียก

นี่คือบั๊กที่ร้ายแรงที่สุดในหัวข้อ "รองรับหลายรุ่น" — มันไม่เตือน ไม่ลดระดับ มันแค่ไม่ทำงาน

### B3-2 · ดริฟท์ของ yaw กับ baseline ที่แช่แข็งทั้งเซสชัน 🔴

`EntryDetectionPolicy` เขียนไว้ชัดว่า *"The baseline is frozen for the whole armed
session — this class never rebaselines"* และเกณฑ์แจ้งเตือนเริ่มต้นคือ **15°**

GAME_ROTATION_VECTOR ไม่มีจุดอ้างอิง yaw สัมบูรณ์ → ความคลาดเคลื่อน yaw สะสมไปเรื่อย ๆ
อาร์มค้างข้ามคืน 8 ชั่วโมงบนชิปที่ดริฟท์แรง มุมสะสมอาจเกิน 15° ได้โดยประตูไม่ได้ขยับ
→ **แจ้งเตือนผิดกลางดึก**

อัตราดริฟท์ต่างกันมากตามชิปเซ็ต **ห้ามเดา ต้องวัดจริง** (งาน T12)

### B3-3 · `fresh = true` ตายตัว ประตูด่านแรกเป็นโค้ดตาย 🟠

บรรทัด 1196 ตั้ง `fresh = true` เสมอ และ `onAccuracyChanged` เป็น `Unit`
`EntryDetectionPolicy` มี Gate 1 ตรวจ `sample.fresh` เป็นด่านแรกสุด — **ด่านนี้ไม่มีวันทำงาน**

ผลจริง: เครื่องที่ตกไปใช้ ROTATION_VECTOR แล้วเข็มทิศยังไม่ปรับเทียบ
(`SENSOR_STATUS_UNRELIABLE`) จะส่งทิศมั่ว ๆ เข้าไปโดยระบบถือว่าเชื่อถือได้เต็มร้อย

### B3-4 · ลายนิ้วมือการปรับเทียบโกหก 🟠

`EntryCommissioningEnvironment.sensorIdentity()` คืนค่า
`"game-rotation-vector/${Build.MANUFACTURER}/${Build.MODEL}"` **ตายตัว**
ไม่ว่าจริง ๆ จะลงทะเบียนตัวไหน

เครื่องที่ตกไปใช้ ROTATION_VECTOR จะบันทึกว่าใช้ game-rotation-vector
→ ระบบตรวจจับการเปลี่ยนแหล่งข้อมูลไม่ได้ → โมเดลบานพับที่เรียนจากเซ็นเซอร์ตัวหนึ่ง
ถูกเอาไปใช้กับอีกตัวโดยไม่บังคับปรับเทียบใหม่ ทั้งที่ระบบออกแบบมาให้บังคับ

## B4. ทางออกที่เสนอ — บันไดความสามารถ 5 ขั้น

แทนที่จะ hardcode ลำดับ ให้ประกาศเป็นนโยบายที่ query ได้ และ**บอกผู้ใช้ว่าเครื่องเขาอยู่ขั้นไหน**

| ขั้น | ใช้อะไร | จุดอ้างอิง yaw | ข้อจำกัด | เกณฑ์/เวลายืนยัน |
|---|---|---|---|---|
| **A** ดีที่สุด | GAME_ROTATION_VECTOR **+ เข็มทิศคอยตรึงดริฟท์** | gyro ระยะสั้น + เข็มทิศระยะยาว | ต้องมีทั้ง gyro และเข็มทิศ | 15° / 750 ms |
| **B** | ROTATION_VECTOR | มีในตัว | โดนโลหะรบกวนใกล้ตำแหน่งปิด | 15° / 750 ms |
| **C** ← *ที่ใช้อยู่ตอนนี้* | GAME_ROTATION_VECTOR ล้วน | **ไม่มี** | ดริฟท์สะสมเมื่ออาร์มนาน | ต้องจำกัดเวลาอาร์ม หรือเตือน |
| **D** | GEOMAGNETIC_ROTATION_VECTOR (ไม่มี gyro) | เข็มทิศล้วน | สัญญาณกวนสูง อัตราต่ำ | ต้องยืด confirmation เช่น 20° / 1500 ms |
| **E** | ไม่มีอะไรเลย | — | **ต้องบล็อกโหมดประตู** พร้อมเหตุผล | — |

### ทำไมต้องผสม ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

จุดที่ต้องเข้าใจให้ตรงกัน: โทรศัพท์ติดอยู่**บนบานประตู** เคลื่อนที่ไปกับประตู

- โลหะที่ติดกับบานประตูเอง (ตัวบานเหล็ก) ให้ค่าเบี่ยงเบน**คงที่** — ถูกดูดซับโดย baseline
  ที่แช่แข็งไว้ ไม่เป็นปัญหา
- โลหะที่ **ไม่** เคลื่อนไปกับโทรศัพท์ — วงกบ บานพับ แผ่นรับลูกบิด แม่เหล็กดูดประตู —
  เปลี่ยนตำแหน่งสัมพัทธ์ขณะประตูแกว่ง ทำให้สนามบิดเบี้ยวไม่เป็นเชิงเส้นกับมุมจริง
  ความคลาดเคลื่อนมักแรงที่สุดใน **ช่วง 15° แรกของการเปิด** ซึ่งคือช่วงที่เกณฑ์ตั้งอยู่พอดี

สรุปเป็นประโยคเดียว: **ไจโรแม่นตรงจุดที่เกณฑ์อยู่ เข็มทิศแม่นตรงจุดที่ไจโรพัง**
จึงต้องใช้ทั้งคู่ — ไจโรวัดมุมช่วงสั้น เข็มทิศทำหน้าที่ตรึงไม่ให้ศูนย์เลื่อนระหว่างอาร์มยาว
เข็มทิศไม่ควรถูกใช้เป็นตัวตัดสินมุมโดยตรง

## B5. เสียงและการสั่นในโหมดประตู — ตอบคำถามโดยตรง

**ถูกต้อง ต้องมี และตอนนี้มันทำงานอยู่แล้ว** — `usedSensorKinds(ENTRY)` รวม
`VIBRATION`, `MICROPHONE`, `LIGHT`, `LOCATION`, `POWER_THERMAL` ครบ
([ProtectionProfilePolicy.kt:309](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/protection/ProtectionProfilePolicy.kt))

### หน้าที่จริงของมันมีสามอย่าง เรียงตามความสำคัญ

**1. แยกการเปิดประตูจริง ออกจากดริฟท์ของเซ็นเซอร์ ← มีค่าที่สุด**
ประตูที่ถูกเปิดจริงย่อมมีแรงสั่นตอนเริ่มขยับเสมอ ส่วนดริฟท์ของไจโร**ไม่มีแรงสั่นเลย**
มุมที่ค่อย ๆ เลื่อนโดยไม่มีการสั่นร่วมในหน้าต่างเดียวกัน = ดริฟท์ แทบแน่นอน
นี่คือยาแก้ตรงจุดสำหรับ B3-2 และเป็นเหตุผลที่แข็งแรงที่สุดในการคงเซ็นเซอร์สั่นไว้ในโหมดประตู

**2. ยกระดับความรุนแรง**
เสียงงัด/กระแทก + ประตูเปิด = พยายามงัด ไม่ใช่คนในบ้านเปิดประตูตามปกติ
กลไกยกระดับมีอยู่แล้วในเอนจิน (`ENTRY_MOUNT_MOVED` ยกเป็น CRITICAL)

**3. เติมหลักฐานในข้อความแจ้งเตือน** ให้เจ้าของตัดสินใจได้เร็วขึ้นว่าจะรีบกลับหรือไม่

### แต่ต้องเป็น "ประกอบ" เท่านั้น ห้ามเป็น "หลัก" — และตอนนี้ยังผิดอยู่ 🔴

`IncidentEngine` มี **ช่องเหตุการณ์ที่ใช้งานอยู่เพียงช่องเดียว** (`activeIncident`)
และ `isPrimaryRole()` เขียนว่า:

```kotlin
role == SensorRole.PRIMARY || role == null      // IncidentEngine.kt:507
```

observation ของไมโครโฟนถูกสร้างขึ้น **โดยไม่ใส่ `role` เลย**
([AudioThreatPipeline.kt:468](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/sensor/audio/AudioThreatPipeline.kt))
→ `role = null` → **ไมโครโฟนทำตัวเป็น "หลัก" เสมอ ไม่ว่าตั้งค่าอย่างไร**

ซ้ำร้าย `openIncident()` ที่ไม่ได้ส่ง `supersede = true` จะ**เขียนทับ** `activeIncident`
โดยไม่ปิดเหตุการณ์เดิม ([IncidentEngine.kt:392](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/protection/IncidentEngine.kt))

**สถานการณ์จริงที่จะพัง:** มีเสียงดังผ่านมาก่อน → เปิดเหตุการณ์ AUDIO ยึดช่องไว้ →
ประตูถูกเปิดจริงหลังจากนั้น → เหตุการณ์ประตูเข้าไปเขียนทับ → เหตุการณ์เสียงค้าง OPEN ไม่มีวันปิด
นี่คือบั๊กตระกูลเดียวกับที่เพิ่งแก้ไปในโหมดไฟเลี้ยง (`c319300`, `8e7f1a5`) แต่ยังไม่ได้แก้ฝั่งประตู

**และไมโครโฟนไม่มีตัวควบคุมในหน้าตั้งค่าเลย** — fusion config ครอบคลุมแค่ 10 source
กลุ่มการเคลื่อนไหว/แสง/แม่เหล็ก/ระยะประชิด เท่านั้น
ดังนั้น "ตั้งไมค์เป็นประกอบ" ยังพูดไม่ได้ในระบบปัจจุบัน

# ภาค D — "ใครเป็นเจ้าภาพ ใครเป็นตัวสนับสนุน" คือแกนกลางของทั้งระบบ

เจ้าของสรุปถูกแล้ว และนี่ควรเป็นหลักคิดที่ทุกโหมดใช้ร่วมกัน แต่**ตอนนี้แนวคิดนี้
ยังทำได้แค่ครึ่งเดียวในโค้ด** — ต้องรู้ก่อนว่าครึ่งไหนหายไป ไม่งั้นออกแบบบนพื้นที่ไม่มีจริง

## D1. "เจ้าภาพ" แปลว่าอะไรในเชิงกลไก

เจ้าภาพ = **สัญญาณที่ได้รับอนุญาตให้เปิดเหตุการณ์ด้วยตัวเอง** ที่เหลือเปิดเองไม่ได้
ต้องอาศัยเจ้าภาพเปิดให้ก่อนแล้วจึงเข้าไปเติมหลักฐาน/ยกระดับ (`primaryPresent` ใน `IncidentEngine`)

ผลพลอยได้สามอย่างที่ตามมาอัตโนมัติเมื่อเลือกเจ้าภาพ:
1. เจ้าภาพทุกตัวต้องปรับเทียบเสร็จก่อนระบบจะเริ่มป้องกัน → **เจ้าภาพยิ่งเยอะ Arm ยิ่งช้า**
2. เจ้าภาพที่เครื่องไม่มี → การตั้งค่าถูกปฏิเสธทั้งชุด (ตัวสนับสนุนแค่ degraded)
3. เจ้าภาพยิ่งเยอะ ยิ่งมีปากทางให้เตือนผิด และยิ่งแย่งช่องเหตุการณ์กันเอง

## D2. ตารางเจ้าภาพที่ควรเป็น (ข้อเสนอ)

| โหมด | เจ้าภาพ | ตัวสนับสนุน | ปิด |
|---|---|---|---|
| **เฝ้ารถ** | มาตรวัดความเร่ง (การสั่น) · เซ็นเซอร์วัดแสง | แกนหมุนทุกตัว · แม่เหล็ก · ระยะประชิด · ไมโครโฟน · ตำแหน่ง | — |
| **เฝ้าประตู** | **แหล่งทิศทางเท่านั้น** (ขั้น A–D ตามภาค B) | การสั่น · ไมโครโฟน · แสง · ตำแหน่ง | — |
| **ไฟเลี้ยง** | ไฟยืนยัน (แสง) · สัญญาณการชาร์จ — ต้องยืนยันสองทาง | — | ทุกตัวที่เหลือ |

หลักที่ยึด: **หนึ่งโหมดประกาศเจ้าภาพชุดเดียวชัดเจน สัญญาณอื่นทั้งหมดห้ามเปิดเหตุการณ์เอง**
โหมดประตูเป็นตัวอย่างที่ชัดที่สุด — เสียงและการสั่นมีค่ามากในฐานะ**ตัวยืนยัน**
(โดยเฉพาะการแยกดริฟท์ออกจากการเปิดจริง ตาม B5 ข้อ 1) แต่ต้องไม่ใช่เจ้าภาพ
เพราะเสียงดังจากถนนไม่ใช่การเปิดประตู

## D3. ช่องโหว่: ตอนนี้ยังตั้งเจ้าภาพได้ไม่ครบทุกสัญญาณ

| สัญญาณ | ตั้งบทบาทได้ไหม | ความจริงตอนนี้ |
|---|---|---|
| 10 source กลุ่มเคลื่อนไหว/หมุน/แม่เหล็ก/แสง/ระยะประชิด | ✅ ตั้งได้ | ทำงานตามที่ตั้ง |
| ไมโครโฟน | ❌ ไม่มีตัวควบคุมเลย | `role = null` → **เป็นเจ้าภาพเสมอ** |
| ตำแหน่ง (GPS) | ❌ | `role = null` → เป็นเจ้าภาพเสมอ |
| สัญญาณสายชาร์จ | ❌ | `role = null` → เป็นเจ้าภาพเสมอ |
| แหล่งทิศทางของโหมดประตู | ❌ | ตั้ง `PRIMARY` ตายตัวในโค้ด |

`isPrimaryRole()` เขียนว่า `role == PRIMARY || role == null` — **ค่าที่ยังไม่ได้กำหนด
ถูกตีความว่าเป็นเจ้าภาพ** ซึ่งกลับด้านกับสิ่งที่ปลอดภัยกว่า ค่าเริ่มต้นที่ถูกต้องคือ
"ยังไม่ได้กำหนด = เปิดเหตุการณ์เองไม่ได้"

แปลว่าวันนี้โหมดเฝ้าประตูมีเจ้าภาพซ่อนอยู่ถึงสี่ตัวโดยไม่มีใครตั้งใจ: แหล่งทิศทาง +
ไมโครโฟน + ตำแหน่ง + สายชาร์จ ทั้งสี่แย่งช่องเหตุการณ์เดียวกันได้ (T14)

## D4. สิ่งที่ต้องทำเพื่อให้แนวคิดนี้เป็นจริงทั้งระบบ

1. **ทุกสัญญาณที่เปิดเหตุการณ์ได้ต้องพก `role` จริงเสมอ** ห้ามมี `null` หลุดเข้าเอนจิน (T14)
2. **กลับค่าเริ่มต้น** — `isPrimaryRole(null)` ต้องเป็น `false` แล้วให้แต่ละแหล่งประกาศตัวเอง
3. **ขยายตารางบทบาทให้ครอบคลุมไมค์/ตำแหน่ง/สายชาร์จ** ไม่ใช่แค่ 10 source ฮาร์ดแวร์
4. **หน้าตั้งค่าแสดงเจ้าภาพของโหมดปัจจุบันไว้บนสุด** ไม่ต้องให้ผู้ใช้ไล่อ่านทีละแถวเอง

### T16 · ทำให้ "เจ้าภาพ" เป็นจริงทั้งระบบ

**ทำ:** ข้อ D4 ทั้งสี่ข้อ · หัวการ์ดแสดง `เจ้าภาพของโหมดนี้: ...`

**ตรวจบนเครื่อง:**
1. หัวการ์ดโหมดเฝ้าประตูขึ้น "เจ้าภาพ: เซ็นเซอร์ทิศทาง" — ตัวเดียว ไม่ใช่สี่ตัว
2. โหมดเฝ้ารถขึ้น "เจ้าภาพ: การสั่น · แสง"
3. ไล่ตรวจว่าไมโครโฟนปรากฏในรายการบทบาทแล้ว และตั้งเป็น "ประกอบ" ได้จริง
4. ทำเสียงดังในโหมดประตู → ไม่เปิดเหตุการณ์เอง (ต่อยอดจาก T14)

# ภาค E — GPS ในโหมดเฝ้ารถ: ของเดิมใช้ได้ดี ห้ามแตะ แต่มีจุดที่ลำดับงานผิดแล้วพัง

**ขอบเขต: งานทั้งหมดในแผนนี้ไม่แก้ตรรกะการติดตามตำแหน่ง** สิ่งที่ต้องทำคือ

## E1. ของเดิมทำงานยังไง (ยืนยันจากโค้ดแล้ว)

```
Arm → ปักหมุดจุดจอด (ParkingAnchor)
    → เฝ้าดูระยะห่างจากหมุด
    → ห่างเกิน ~100 ม. + ยืนยัน 2 fix ห่างกัน 15-60 วิ + ความแม่นยำ ≤ 100 ม.
    → ยิงข้อความ "กำลังถูกเคลื่อนย้าย" + เปิด Telegram live location 15 นาที
    → อัปเดตตำแหน่งทุก ≥10 วิ หรือเมื่อขยับ ≥10 ม.
```

เกณฑ์ 100 ม. / 2 fix / 15-60 วิ เป็นการกันเตือนผิดจากความคลาดเคลื่อนของ GPS
ซึ่งออกแบบมาดีแล้ว **ไม่ควรไปลดลง**

## E2. 🔴 จุดที่ลำดับงานผิดแล้ว GPS พังเงียบ

นี่คือประเด็นสำคัญที่สุดของภาคนี้

`isPrimaryRole()` เขียนว่า `role == PRIMARY || role == null` และ observation ของตำแหน่ง
ถูกสร้าง**โดยไม่ใส่ `role`** ([ProtectionRuntimeGraph.kt:374](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/protection/ProtectionRuntimeGraph.kt))

แปลว่า **การแจ้งเตือน GPS ทำงานได้ทุกวันนี้เพราะค่าเริ่มต้น `null` ถูกนับเป็นเจ้าภาพพอดี**

T14/T16 ที่เสนอไว้จะกลับค่าเริ่มต้นนี้ให้ `null = เปิดเหตุการณ์เองไม่ได้`
**ถ้าทำโดยไม่ประกาศให้ตำแหน่งเป็นเจ้าภาพของโหมดเฝ้ารถไปพร้อมกัน
การเตือนว่ารถถูกเคลื่อนย้ายจะเงียบไปทั้งหมด** โดยไม่มี error ไม่มี crash

### กติกาบังคับสำหรับ T14/T16

1. คอมมิตเดียวกันต้องประกาศ `LOCATION = เจ้าภาพ` สำหรับ **เฝ้ารถ** เสมอ
   (โหมดประตู = สนับสนุน · โหมดไฟเลี้ยง = ไม่ใช้อยู่แล้ว)
2. เขียนเทสต์ล็อกพฤติกรรมนี้ไว้**ก่อน**แตะ `isPrimaryRole()`:
   "ยืนยันการเคลื่อนย้ายในโหมดเฝ้ารถ ต้องเปิดเหตุการณ์และเริ่ม live location"
3. ห้ามแยก T14 ออกเป็นสองคอมมิตโดยให้คอมมิตแรกกลับค่าเริ่มต้นทิ้งไว้

## E3. งานอื่นในแผนนี้ กระทบ GPS ไหม

|---|---|---|

## E4. เรื่องที่สังเกตเห็น แต่ยังไม่เสนอให้แก้ (ของเดิมใช้ได้ดี)

บันทึกไว้เฉย ๆ ให้ตัดสินใจภายหลัง ไม่ได้อยู่ในลำดับงาน:

- live location เปิด **15 นาที ต่อหนึ่งเซสชันอาร์ม** และ `pursuitAttempted` กันไม่ให้เริ่มซ้ำ
  ถ้าถูกขับออกไปนานกว่านั้นจะตามต่อไม่ได้ (Telegram รองรับได้ถึง 8 ชม.)
- การติดตามเริ่มหลังเคลื่อนเกิน ~100 ม. เท่านั้น แม้จะมีเหตุการณ์งัดแงะระดับวิกฤตเกิดก่อนแล้ว

ทั้งสองข้อเป็นการ**ขยายความสามารถ** ไม่ใช่การซ่อมของเสีย จึงไม่ควรเอาไปปนกับงานชุดนี้
