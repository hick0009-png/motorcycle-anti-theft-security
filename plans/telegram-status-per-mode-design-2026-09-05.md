# Design — `/status` ต่อโหมด: ตอบเฉพาะโหมดที่กำลังเฝ้าอยู่ (2026-09-05)

สถานะ: **ร่างสเปก เจ้าของเคาะครบแล้ว (§14) ยังไม่ได้ลงมือ** · ต่อยอดจาก [checkpoint-2026-08-22-three-profiles-foundation.md](checkpoint-2026-08-22-three-profiles-foundation.md)
ทุกบรรทัดที่อ้างถึงพฤติกรรมวันนี้ อ้างจากไฟล์จริงพร้อมเลขบรรทัด ไม่ใช่ความจำ
ตัวอย่างข้อความในเอกสารนี้นับความยาวจริงแล้ว (§7)

## 1. ปัญหาที่ทำให้ต้องยกเครื่อง ไม่ใช่แค่แต่ง

วันนี้ `/status` ตอบด้วยแม่แบบเดียว ไม่ว่าเจ้าของจะเลือกโหมดไหน:
`TelegramCommandHandler.kt:63` → `statusFormatter.format(coordinator.snapshot.value)` แล้ว
`ProtectionStatusFormatter.kt:47-52` ไล่พิมพ์เซ็นเซอร์ทั้งห้าชนิดตายตัวเสมอ

**ทั้งแพ็กเกจ `telegram/` ไม่มีการอ้างถึง `armedProfileSnapshot` แม้แต่ที่เดียว** — `/status` ไม่รู้ว่าโหมดคืออะไร

ผลที่ตามมามีสี่อย่าง เรียงจากอันตรายที่สุด:

### 1.1 รายงานว่าเซ็นเซอร์เสีย ทั้งที่โหมดปิดมันไว้เอง

โหมดไฟเลี้ยงตั้งใจปิด `VIBRATION` / `MICROPHONE` / `LOCATION`
(`ProtectionProfilePolicy.kt:494-499` → `SensorRole.OFF`)
รันไทม์จึงไม่ลงทะเบียนมันเลย และ `sensorHealth` ไม่มีคีย์ `LOCATION`

`ProtectionStatusProjection.kt:803-812` เจอคีย์หายแล้วคืน:

```
❌ GPS: ไม่พร้อมใช้งาน
```

พร้อม `IssueRecommendation("❌ GPS: ไม่พร้อมใช้งาน", "ตรวจสอบระบบพิกัดตำแหน่งของเครื่อง")`
เมื่ออาร์มอยู่ — คือ **สั่งให้เจ้าของไปแก้ GPS ในโหมดที่ไม่ใช้ GPS**

เรามีเจตนานี้ถูกต้องแล้วในที่หนึ่ง: `unhealthySensorReasons()` (`ProtectionCoordinator.kt:1413-1417`)
กรองด้วย `usedSensorKinds` ก่อนนับ degradation — คอมเมนต์ของมันเขียนไว้เองว่า
*"A sensor the armed profile does not detect with must never degrade the armed state"*
**แต่ `/status` ไม่ได้รับกฎข้อนี้ไปด้วย** นี่คือรอยที่กว้างที่สุดของงานนี้

### 1.2 ป้ายโหมดเป็นค่าคงที่ที่พูดแทนทุกโหมด

`ProtectionStatusProjection.kt:166`

```kotlin
val sensitivityTh = "[ 🏃 การเคลื่อนไหว ]\nความไวการตรวจจับ: ${snapshot.sensitivityLevel}/10"
```

เจ้าของที่เฝ้าประตูอยู่ ได้ป้าย `[ 🏃 การเคลื่อนไหว ]` และ "ความไว 8/10"
ทั้งที่โหมดประตูตัดสินด้วย **องศาและเวลาค้าง** ไม่ได้ตัดสินด้วยเลข 1-10 ตัวนั้นเลย
ข้อความ `/help` ยอมรับเรื่องนี้อยู่แล้ว (`UserGuidance.kt:284`: *"ใช้ได้เฉพาะเซ็นเซอร์ที่รองรับในโหมดยานพาหนะ"*)
แต่ `/status` ยังพิมพ์มันให้ทุกโหมด

### 1.3 ตัวหาร `/5` เป็นค่าคงที่ห้าที่

`ProtectionStatusProjection.kt:351-355` และ `:362` ฝัง `5` ไว้ตรง ๆ
โหมดไฟเลี้ยงใช้เซ็นเซอร์สองชนิด เต็มร้อยของมันคือ `2/2` ไม่ใช่ `2/5`
วันนี้เจ้าของเห็น `2/5` แล้วสรุปว่าระบบพังไปสามส่วนห้า ทั้งที่ครบทุกอย่าง
เทสต์ก็ตรึงความเข้าใจผิดนี้ไว้แล้ว: `ProtectionStatusTruthPathIntegrationTest.test01_freshArmedLiveFixShowsActive5Of5`

### 1.4 ไม่มีอะไรของโหมดนั้นเลยสักบรรทัด

สิ่งที่เจ้าของอยากรู้จริง ๆ ในแต่ละโหมด ไม่มีอยู่ใน `/status` วันนี้แม้แต่อย่างเดียว:

| โหมด | คำถามจริงของเจ้าของ | มีข้อมูลในโค้ดแล้วที่ | อยู่ใน `/status` วันนี้ |
|---|---|---|---|
| ประตู | "ตอนนี้ประตูเปิดกี่องศา" | `EntryArmedSessionController.liveAngleDeg()` | ❌ |
| ประตู | "อาร์มไว้ 9 ชม. ยังเชื่อได้อยู่ไหม" | `EntryDriftBudgetPolicy` + `driftBudgetLine()` | ❌ |
| ประตู | "เฝ้าแบบเสียง+ขยับ หรือแบบวัดองศา" | `EntryWatchLevel` | ❌ |
| ไฟเลี้ยง | "ตอนนี้ไฟยืนยันสว่างหรือดับ" | `PowerArmedSessionController.activeWitnessModel()` | ❌ |
| ไฟเลี้ยง | "กำลังนับถอยหลังยืนยันไฟดับอยู่หรือเปล่า" | `PowerArmedSessionController.nextConfirmationAtMs()` | ❌ |
| ยานพาหนะ | "รถขยับไปจากจุดจอดกี่เมตร" | `MovementDisplacementPolicy` | ❌ |

> **สรุปข้อ 1:** ปัญหาไม่ใช่ "ข้อมูลเยอะไป" แต่เป็น **ข้อมูลของโหมดอื่นดังกลบข้อมูลของโหมดนี้
> และบางบรรทัดพูดสิ่งที่ไม่จริงในโหมดนี้** การตัดบรรทัดออกเฉย ๆ แก้ได้แค่ครึ่งเดียว
> อีกครึ่งคือของที่ยังไม่เคยมี

## 2. `/status` ฉบับใหม่ต้องตอบสี่คำถาม ตามลำดับนี้

เจ้าของกดคำสั่งนี้ตอนไม่ได้อยู่กับรถ/ประตู มือถือเครื่องเดียว อ่านบนหน้าจอล็อก:

1. **ตอนนี้เฝ้าอะไรอยู่** — โหมดไหน เปิดเฝ้าอยู่จริงไหม นานเท่าไร
2. **สิ่งที่โหมดนี้เฝ้าอยู่ ตอนนี้เป็นอย่างไร** — ประตูปิดอยู่ไหม ไฟยังมาไหม รถอยู่ที่เดิมไหม
3. **เชื่อคำตอบข้อ 2 ได้แค่ไหน** — เซ็นเซอร์ครบไหม เกินเพดานเวลาที่วัดไว้หรือยัง ช่องทางแจ้งเตือนยังถึงไหม
4. **มีอะไรต้องทำไหม** — ปัญหา + วิธีแก้ที่ลงมือได้จากตรงนั้น

**ลำดับนี้คือลำดับส่วนในข้อความ** ข้อ 1-2 ต้องอยู่ในสามบรรทัดแรกเสมอ
เพราะเจ้าของครึ่งหนึ่งอ่านแค่ notification preview แล้วปิด

## 3. โครงใหม่: กระดูกสันหลังร่วม + เนื้อเฉพาะโหมด

```
┌─ ส่วน A · ตัวตน (ทุกโหมดเหมือนกัน)      "🛡️ โหมด<X> · <สถานะ> / เฝ้ามาแล้ว N"
├─ ส่วน B · โหมดนี้เฝ้าอะไร (สร้างจากตาราง signalRoles)
├─ ส่วน C · เนื้อเฉพาะโหมด  ◄── ของใหม่ทั้งหมดอยู่ตรงนี้ (§5)
├─ ส่วน D · เซ็นเซอร์ที่โหมดนี้ใช้ (กรองแล้ว + ติดป้ายบทบาท)
├─ ส่วน E · ช่องทางแจ้งเตือน + แบตเตอรี่ (ทุกโหมดเหมือนกัน)
├─ ส่วน F · เหตุการณ์ล่าสุด
└─ ส่วน G · ปัญหา + วิธีแก้ (กรองด้วย usedSensorKinds แล้ว)
```

**A, B, E, F, G ใช้โค้ดร่วมกัน** — งานนี้ไม่ได้เขียนสามฟอร์แมตเตอร์
`ProtectionStatusFormatter` ยังเป็นตัวเดียว แต่ส่วน C มาจาก `ModeSectionRenderer` ที่เลือกตาม `ProtectionProfile`

**ส่วน E ย้ายลงล่าง** (วันนี้อยู่บนสุดที่ `ProtectionStatusFormatter.kt:37-40`) — เคาะแล้ว §14.1
เหตุผล: "Telegram เชื่อมต่ออยู่" เป็นคำตอบของข้อ 3 ไม่ใช่ข้อ 1
เจ้าของที่เพิ่งได้ข้อความนี้ทาง Telegram รู้อยู่แล้วว่า Telegram ใช้ได้

## 4. ⚠️ ข้อจำกัดที่ต้องแก้ก่อน: snapshot ไม่รู้จักโหมดตอนที่ยังไม่อาร์ม

`ProtectionSnapshot.armedProfileSnapshot` (`ProtectionModels.kt:244`) **เป็น null ทุกครั้งที่ไม่ได้อาร์ม**
มันถูกแช่แข็งตอน `arm()` เท่านั้น (`ProtectionCoordinator.kt:325`)

แต่ `/status` ถูกถามตอนไม่ได้อาร์มบ่อยพอ ๆ กับตอนอาร์ม — และคำถาม
*"ทำไมกดอาร์มไม่ได้"* มีความหมายเฉพาะเมื่อรู้ว่าโหมดที่เลือกไว้คืออะไร
`selectedProfile` อยู่ใน `ProtectionProfileRepository` ซึ่ง `telegram/` เข้าไม่ถึง

นอกจากนั้น `ArmedProfileSnapshot` **ไม่ได้เก็บ `EntryWatchLevel`** ด้วย
(มันอยู่ใน `ProtectionCoordinator.armedEntryLevel` ซึ่งเป็น private `AtomicReference`, `:64`)
ทั้งที่โหมดประตูสองระดับให้คำตอบคนละแบบสิ้นเชิง

### 4.1 ทางเลือกสามทาง

| ทาง | วิธี | ปัญหา |
|---|---|---|
| A | ให้ formatter ถาม `ProtectionProfileRepository` เอง | formatter เลิกเป็น pure function เทสต์ที่มีอยู่ต้องมี fake repository ทั้งหมด |
| B | เพิ่มฟิลด์ลง `ProtectionSnapshot` | ✅ เลือกทางนี้ |
| C | ส่ง context เข้า `TelegramCommandHandler` ตอนสร้าง | ค่าจะค้างตั้งแต่ตอนต่อ bot สลับโหมดแล้วไม่อัปเดต |

**เลือก B** เพราะ `/status` ต้องตอบได้แม้ตอน `OFFLINE`/`SETUP_REQUIRED` และเพราะ
formatter ที่รับ snapshot ตัวเดียวแล้วคืน string คือสิ่งที่ทำให้เทสต์ปัจจุบันอ่านออก

### 4.2 ⚠️ กับดัก: ค่าที่เปลี่ยนทุกวินาที ห้ามใส่ลง snapshot

`liveAngleDeg()` เปลี่ยนทุกตัวอย่างที่ไจโรส่งมา `witnessLux` ก็เช่นกัน
`SnapshotProjectionGate` ยุบการ emit ด้วย `ProjectionKey` (`SnapshotProjectionGate.kt:30-40`)
**ถ้ามุมสดเข้าไปอยู่ใน key ทุกตัวอย่างจะกลายเป็น "semantic change"**
→ snapshot emit ถี่ระดับเซ็นเซอร์ → เขียน durable snapshot รัว → กินแบตในโหมดที่ขายว่าเฝ้าข้ามคืนได้

จึงต้อง **แยกแหล่งข้อมูลเป็นสองชั้น**:

```
ชั้น 1 · ข้อเท็จจริงที่คงทน  → ลง ProtectionSnapshot, เข้า ProjectionKey ตามปกติ
         โหมดที่เลือก, ระดับการเฝ้า, setupState, การรองรับของเครื่อง,
         เกณฑ์มุม/เกณฑ์ lux/เวลายืนยัน, ผลวัด drift, fingerprint โมเดล

ชั้น 2 · ค่าอ่านสด          → ไม่ลง snapshot เลย ดึงตอนถูกถามเท่านั้น
         มุมขณะนี้, lux ขณะนี้, การนับถอยหลังยืนยัน, ระยะห่างจากจุดจอด
```

ชั้น 2 เข้ามาทาง supplier ที่ handler เรียก ณ เวลาตอบคำสั่ง:

```kotlin
fun interface ModeLiveReadings {
    /** null = โหมดนี้ไม่มีค่าอ่านสด หรืออ่านไม่ได้ตอนนี้ — ไม่ใช่ error */
    fun read(profile: ProtectionProfile): ModeLiveSample?
}
```

`/status` ถูกถามเป็นครั้ง ๆ (เจ้าของพิมพ์) ไม่ใช่ทุกวินาที การอ่านสดตอนถูกถามจึงถูกและตรงกว่า
กฎเดียวกับที่ `/where` ใช้อยู่แล้ว (`OnDemandLocationFinder`, `TelegramCommandHandler.kt:66-77`)

### 4.3 ฟิลด์ใหม่ (ชั้น 1)

```kotlin
/** โหมดที่ /status ต้องพูดแทน แม้ตอนไม่ได้อาร์ม */
data class ProtectionModeContext(
    val selectedProfile: ProtectionProfile?,      // null = ลูกค้าเก่าที่ยังไม่เคยเลือกโหมด
    val entryLevel: EntryWatchLevel?,             // non-null เฉพาะ ENTRY
    val setupState: ProfileSetupState,
    val support: ProfileDeviceSupport,
    val switchingTo: ProtectionProfile?,          // จาก ProfileSwitchTransaction
    val modeFacts: ModeFacts?,                    // เกณฑ์/โมเดล ต่อโหมด (sealed)
)
```

`ProtectionSnapshot` เพิ่มฟิลด์เดียว `val modeContext: ProtectionModeContext? = null`
ค่า default เป็น null แปลว่า **โค้ดและเทสต์ทุกตัวที่มีอยู่คอมไพล์ผ่านโดยไม่แก้**
และ formatter fallback เป็นพฤติกรรมเดิม (§8.1)

`ProjectionKey` เพิ่ม `modeContext` เข้าไปด้วย — โหมดเปลี่ยนคือ semantic change ที่ต้อง emit ทันที

## 5. เนื้อเฉพาะโหมด (ส่วน C)

กฎร่วมสามข้อ ใช้กับทุกโหมด:

1. **ทุกบรรทัดต้องมีรูปแบบ "ไม่รู้"** ห้ามหายไปเงียบ ๆ — ถ้าอ่านค่าไม่ได้ให้พิมพ์
   `มุมขณะนี้: อ่านไม่ได้ (ยังไม่ได้อาร์ม)` ไม่ใช่ข้ามบรรทัดนั้น
   บรรทัดที่หายไปคือบรรทัดที่เจ้าของไม่มีทางรู้ว่าเคยมี
2. **ทุกตัวเลขต้องมาพร้อมเกณฑ์ที่มันถูกเทียบ** `0.8°` ไม่มีความหมาย `0.8° (เกณฑ์ 15°)` มี
3. **ห้ามพิมพ์หน่วยดิบที่เจ้าของแปลไม่ออก** ไม่มี `quaternion` ไม่มี `epoch ms` ไม่มี fingerprint เต็ม ๆ

### 5.1 โหมดยานพาหนะ

| บรรทัด | ที่มา | ตอนไม่มีค่า |
|---|---|---|
| ความไวการตรวจจับ N/10 | `snapshot.sensitivityLevel` | มีเสมอ |
| พิกัดล่าสุด + ความแม่นยำ + อายุ | `LocationHealthDetail` | `ยังไม่มีพิกัด (กำลังหาสัญญาณ)` |
| ห่างจากจุดจอด N เมตร **(อยู่ในเฟสแรก · เคาะแล้ว §14.2)** | `MovementTrackingStore` + `MovementDisplacementPolicy` | `ยังไม่ได้ตั้งจุดจอด (ยังไม่ได้อาร์ม)` |
| การไล่ตามสด | `LivePursuitCoordinator` | `ไม่ได้เปิดอยู่` |
| สายชาร์จ | `ChargingState` | `ไม่ทราบ` |

**เหตุผลที่ความไว 1-10 อยู่เฉพาะโหมดนี้:** มันปรับเกณฑ์ของตัวตรวจการสั่นจริง ๆ
ในอีกสองโหมดมันไม่ได้ถูกอ่านเลย การพิมพ์มันคือการเชิญให้เจ้าของสั่ง `/sensitivity`
แล้วสงสัยว่าทำไมไม่มีอะไรเปลี่ยน

### 5.2 โหมดประตูและทางเข้า

แตกเป็นสองแบบตาม `EntryWatchLevel` — คนละคำตอบ ไม่ใช่คนละคำ

**`DOOR_ANGLE`:**

| บรรทัด | ที่มา | ตอนไม่มีค่า |
|---|---|---|
| เกณฑ์แจ้งเตือน `X° ค้าง Y ms` | `EntryProfileSettings.angleThresholdDegrees/openConfirmationMs` | มีเสมอ |
| ถือว่าปิดเมื่อ `< Z° นาน W วินาที` | `closeThresholdDegrees/closeConfirmationMs` | มีเสมอ |
| มุมขณะนี้ (ชั้น 2) | `EntryArmedSessionController.liveAngleDeg()` | `อ่านไม่ได้ (ยังไม่ได้อาร์ม)` |
| โมเดลบานพับ ปรับเทียบเมื่อไร + ใช้แหล่งไหน | `EntryHingeModel` | `ยังไม่ได้ปรับเทียบ` |
| **เพดานเวลาที่เชื่อได้** | `EntryDriftBudgetPolicy.evaluate()` + `driftBudgetLine()` | `ยังไม่ได้วัดการไหลของเครื่องนี้` |

**บรรทัดเพดานเวลาคือเหตุผลข้อเดียวที่คุ้มกับงานทั้งหมดนี้**
วันนี้เจ้าของที่อาร์มประตูไว้ 9 ชั่วโมงบนเครื่องที่วัดได้ว่าเชื่อได้ 8 ชั่วโมง **ไม่มีทางรู้เลย**
เขาจะได้แจ้งเตือนที่เกิดจากมุมไหลเอง แล้วเชื่อว่ามีคนเปิดประตู — หรือแย่กว่านั้น
เขาจะเลิกเชื่อการแจ้งเตือนของแอปทั้งหมดหลังจากเจอครั้งที่สาม

`/status` ต้องเทียบสองตัวเลขนี้เอง แล้วยกระดับเป็น **ปัญหาในส่วน G** เมื่อเกิน:

```
⚠️ เฝ้าต่อเนื่องได้ราว 8 ชั่วโมง แต่ตอนนี้อาร์มมาแล้ว 9 ชั่วโมง 40 นาที
เกินเพดานแล้ว การแจ้งเตือนหลังจากนี้อาจเกิดจากมุมที่ไหลเอง ไม่ใช่ประตูเปิด
วิธีแก้: สั่ง /disarm แล้ว /arm ใหม่เพื่อเริ่มนับมุมใหม่
```

ข้อความ `driftBudgetLine()` มีอยู่แล้วครบทั้งสี่ verdict (`PresentationTextCatalog.kt:362-375`)
งานนี้คือ **พาไปถึง Telegram** ไม่ใช่เขียนคำใหม่

#### 5.2.1 ⏰ ทักเจ้าของเองเมื่อเลยเพดาน — เคาะแล้ว: **แบบ ข** (§14.4)

ไม่รอให้ถาม `/status` พอเลยเพดานเมื่อไร **ส่งข้อความหาเจ้าของหนึ่งครั้ง**
เหตุผลที่ชนะข้อโต้แย้งเรื่อง "กวน": เจ้าของที่ไม่ถาม คือเจ้าของที่ไม่รู้ว่าต้องถาม
และราคาของการไม่ทักไม่ใช่แค่เตือนผิดหนึ่งครั้ง แต่คือเจ้าของเลิกเชื่อการแจ้งเตือนทั้งหมด

**ยิงเมื่อไร — ไม่ต้องตั้ง scheduler ใหม่**

มี tick อยู่แล้ว: `HeartbeatPinger` เต้นทุก **15 นาที** (`HeartbeatPinger.kt:113`)
ตรวจตรงนั้น ช้าสุด 15 นาทีบนเพดาน 8 ชั่วโมง = คลาด 0.3% ยอมรับได้

⚠️ **ห้ามใช้ `PursuitExpiryScheduler` แบบ `delay(8 ชม.)`** ถึงจะดูตรงกว่า —
coroutine `delay` ยาว 8 ชั่วโมงไม่รอด doze และไม่รอดโปรเซสตาย
ซึ่งเป็นสองสถานการณ์ที่โหมดเฝ้าข้ามคืนเจอเป็นปกติ tick ที่มีอยู่แล้วทนกว่า

**ยิงกี่ครั้ง — หนึ่งครั้งต่อการอาร์มหนึ่งครั้ง ไม่ยิงซ้ำ**

ผูกกับ `armedSessionId` (`ArmedProfileSnapshot.armedSessionId`) เก็บ id ที่ทักไปแล้วลง durable
storage ข้าง ๆ snapshot — โปรเซสตายแล้วฟื้นมาต้องไม่ทักซ้ำ และการ `/disarm` แล้ว `/arm` ใหม่
ได้ session id ใหม่ จึงทักได้อีกครั้งโดยอัตโนมัติ ซึ่งถูกต้องแล้ว

**ยิงเฉพาะกรณีไหน — เฉพาะ `Limited` เท่านั้น**

| verdict | ผลที่ `ProfileDeviceSupportPolicy` | ทักไหม |
|---|---|---|
| `Trustworthy` | `Supported` | ❌ ไม่มีเพดานให้เลย |
| `Limited` | `Degraded(DRIFT_LIMITS_SESSION, trustedHours)` (`:138-140`) | ✅ **นี่คือกรณีเดียว** |
| `Unusable` | `Unsupported(DRIFT_TOO_FAST)` (`:133-135`) | ❌ อาร์มไม่ได้ตั้งแต่แรก |
| `NotMeasured` | `Supported` | ❌ ไม่มีตัวเลขให้พูด |

**ส่งทางไหน — Telegram อย่างเดียว ไม่ใช้ SMS สำรอง**

นี่คือคำแนะนำ ไม่ใช่การแจ้งเหตุ ถ้าเน็ตล่มจนต้องพึ่ง SMS แปลว่าเจ้าของมีปัญหาที่ใหญ่กว่านี้อยู่
และการเผาโควตา SMS ไปกับข้อความเตือนล่วงหน้าคือการทำให้ SMS ใช้ไม่ได้ตอนที่ต้องใช้จริง

**ข้อความ**

```

หลังจากนี้มุมอาจไหลเองจนแจ้งเตือนทั้งที่ประตูไม่ได้เปิด
```

   แต่ไม่รู้จักขอบส่วน ต้องส่งเป็นสอง `reply()` เองแทนที่จะพึ่งการตัดอัตโนมัติ
3. ถ้าเกินสองข้อความ ให้ยุบส่วน G เหลือสามปัญหาแรก + `(อีก N ข้อ ดูในแอป)`

## 8. สถานะขอบที่ต้องออกแบบให้ครบ ไม่ใช่ปล่อยให้ fallback

### 8.1 ยังไม่ได้เลือกโหมด (`modeContext == null` หรือ `selectedProfile == null`)

ลูกค้าเก่าที่อัปเกรดมาแล้วยังไม่เคยเปิดหน้าเลือกโหมด — `ProtectionCoordinator` รองรับกรณีนี้ไว้แล้ว
(`:151-153` "legacy customer with no selected profile keeps the previous mutable behavior")

`/status` ต้อง **พิมพ์แบบเดิมทั้งห้าชนิด** พร้อมบรรทัดนำหน้าที่พูดตรง ๆ:

```
⚠️ ยังไม่ได้เลือกโหมดการใช้งาน — รายงานนี้จึงแสดงเซ็นเซอร์ทั้งหมด
เปิดแอปแล้วเลือกโหมดเพื่อให้รายงานตรงกับสิ่งที่คุณเฝ้าจริง
```

ห้ามเดาโหมดจากเซ็นเซอร์ที่เห็น การเดาผิดในหน้าจอสถานะแย่กว่าการบอกว่ายังไม่ได้เลือก

### 8.2 กำลังสลับโหมด (`switchTransaction != null`)

ระหว่างสลับ โหมดเก่าหยุดแล้วแต่โหมดใหม่ยังไม่อาร์ม (`ProfileSwitchPhase` 4 เฟส)
ต้องพูดว่า **ตอนนี้ไม่มีอะไรเฝ้าอยู่** ไม่ใช่พูดแทนโหมดใดโหมดหนึ่ง:

```
🛡️ กำลังสลับโหมด: ยานพาหนะ → ประตูและทางเข้า
⚠️ ระหว่างนี้ยังไม่มีการเฝ้า สั่ง /arm เมื่อสลับเสร็จ
```

### 8.3 เครื่องนี้รองรับโหมดนี้ไม่ได้/ได้ไม่เต็ม (`ProfileDeviceSupport`)

`Degraded` → พิมพ์สิ่งที่เสียไปด้วย `profileSupport()` ที่มีอยู่แล้ว (`PresentationTextCatalog.kt:180`)
`Unsupported` → `/status` ต้องบอกว่าอาร์มไม่ได้และเพราะอะไร ไม่ใช่รายงานเซ็นเซอร์เฉย ๆ

### 8.4 `SETUP_REQUIRED`

ใช้ `setupBlocker` ที่มีอยู่แล้ว (`ProtectionModels.kt:246`) → `toGuidanceCode(setupBlocker)`
งานนี้ทำเสร็จแล้วใน `ProtectionStatusFormatter.kt:88-107` แค่ต้องพาไปโผล่ในส่วน C ของโหมดนั้น

### 8.5 `OFFLINE`

ส่วน C ทั้งหมดเป็น "ไม่ทราบ" ตามกฎ §5 ข้อ 1 แต่ **ส่วน A ยังต้องบอกโหมด**
เพราะ `modeContext` อยู่ในชั้น 1 ซึ่งคงทน — เจ้าของต้องรู้ว่าอะไรจะกลับมาทำงานเมื่อเครื่องกลับมา

## 11. เทสต์ที่ต้องมี

1. `powerModeNeverReportsGpsAsAFault` — โหมดไฟเลี้ยง + `sensorHealth` ไม่มีคีย์ `LOCATION`

2. `powerModeCountsOutOfTwo` — เจอ `2/2` ห้ามเจอ `/5`
3. `entryDoorAngleModeNeverPrintsSensitivityScale` — ห้ามเจอ `ความไวการตรวจจับ`
4. `entryLevelOneNeverPrintsAnAngleThreshold` — `SOUND_AND_MOVEMENT` ห้ามเจอ `°`
5. `entrySessionPastDriftCeilingRaisesAnIssue` — อาร์ม 9 ชม. เพดาน 8 ชม. → ต้องมีในส่วน G
6. `entryDoorAngleListsOrientationAsHostNotVibration` — ข้อยกเว้น §6
7. `noSelectedProfileFallsBackToTheOldReportAndSaysSo` — §8.1
8. `switchingProfileSaysNothingIsWatching` — §8.2
9. `everyModeSectionHasAnUnknownRendering` — parametrized ทั้งสามโหมด ตั้งค่า null ทุกช่อง
   → ต้องได้จำนวนบรรทัดเท่าเดิม (พิสูจน์กฎ §5 ข้อ 1)
10. `noModeExceedsOneTelegramMessageInTheHealthyCase` — ตรึงตัวเลข §7
11. `sensorRolesInStatusMatchProtectionProfilePolicy` — parametrized ทุกโหมด×ทุกระดับ
    เทียบกับ `signalRoles()` โดยตรง กันไม่ให้ formatter มีตารางของตัวเองอีก

เทสต์ข้อ 11 คือข้อที่ทำให้ปัญหานี้ไม่กลับมา ที่เหลือคือแก้อาการ

เพิ่มสำหรับ S9 (§5.2.1):

12. `ceilingWarningFiresOncePerArmedSession` — เรียก policy สิบครั้งด้วย session id เดิม → ได้ข้อความครั้งเดียว
13. `ceilingWarningReturnsAfterReArm` — session id ใหม่ → ทักได้อีก
14. `ceilingWarningOnlyForLimitedVerdict` — parametrized ทั้งสี่ verdict → มีแค่ `Limited` ที่คืนข้อความ
15. `ceilingWarningSurvivesProcessRestart` — โหลด `lastWarnedSessionId` จาก durable แล้วต้องไม่ทักซ้ำ

## 12. ไม่ทำในเฟสนี้

- `/status <โหมด>` ถามโหมดที่ไม่ได้ใช้อยู่ — วันนี้ `RemoteCommand.parse` ปฏิเสธ argument
  (`RemoteCommand.kt:31`) คงไว้อย่างนั้น เพิ่มทีหลังได้โดยไม่ต้องรื้อ
- ปุ่ม inline keyboard
- ทำให้ `ProtectionStateTelegramNotifier` รู้จักโหมด (แจ้งเตือนตอนเปลี่ยนสถานะยังพูดกลาง ๆ อยู่)
- แปล `/status` เป็นภาษาอื่น
- เปลี่ยนสิ่งที่ **แอป** แสดง — เอกสารนี้พูดถึง Telegram อย่างเดียว
- **ข้อความ heartbeat ทุก 15 นาที** (`HeartbeatPinger.sendHeartbeatPing()`) ยังพูดกลาง ๆ
  ว่า "Armed / Disarmed" ไม่บอกโหมด — มันมีอาการเดียวกับ `/status` แต่เป็นงานคนละชิ้น
  S9 ไปยืมแค่ *จังหวะ* ของมัน ไม่ได้แก้ข้อความของมัน

## 14. สี่ข้อที่เจ้าของเคาะแล้ว (2026-09-05)

### 14.1 ✅ ย้ายส่วน Service/Telegram ลงล่าง

ที่ว่างสามบรรทัดแรกเป็นของ "โหมดไหน · เฝ้าอะไร · ตอนนี้เป็นยังไง"
→ ผลกับสเปก: §3 (ลำดับส่วน), §13 ตัวอย่างทั้งสามอันสะท้อนแล้ว, งานอยู่ใน S4

### 14.2 ✅ เอาบรรทัด "ห่างจากจุดจอด" ตั้งแต่เฟสแรก

รับว่าเป็นอันเดียวที่ต้องแตะ `MovementTrackingStore` แลกกับการที่โหมดยานพาหนะ
ตอบคำถามที่เจ้าของถามจริง ๆ ได้ ("รถยังอยู่ที่เดิมไหม") ไม่ใช่แค่รายงานว่า GPS ทำงาน
→ ผลกับสเปก: §5.1 ยืนยันแล้ว งานอยู่ใน S5

### 14.3 ✅ SMS สำรองโชว์เบอร์บางส่วน `08x-xxx-xx89`

เจ้าของต้องยืนยันได้ว่าตั้งเบอร์ถูกตัว โดยไม่เปิดเบอร์เต็มในห้องแชท
→ ผลกับสเปก: §13.1 เป็นรูปแบบที่อนุมัติแล้ว **ห้ามพิมพ์เบอร์เต็มทุกกรณี**

### 14.4 ✅ แบบ ข — เกินเพดาน drift แล้วทักเจ้าของเอง

ไม่รอให้ถาม `/status` ยิงหนึ่งครั้งต่อการอาร์มหนึ่งครั้ง
→ ผลกับสเปก: เพิ่ม §5.2.1 เต็มรูปแบบ + ขั้น S9 + เทสต์ข้อ 12-15
ตัดสินใจย่อยที่ตามมาและตัดสินไปแล้วใน §5.2.1: ใช้ tick 15 นาทีของ `HeartbeatPinger` ที่มีอยู่
(ไม่ตั้ง scheduler ยาว 8 ชม. เพราะไม่รอด doze), ผูกกับ `armedSessionId`, ยิงเฉพาะ verdict
`Limited`, ส่ง Telegram อย่างเดียวไม่กิน SMS สำรอง
