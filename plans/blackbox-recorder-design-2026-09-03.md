## 0. ปัญหาที่กำลังแก้

เมื่อเกิดเหตุจริงกับผู้ใช้ ต้องตอบให้ได้ว่า **"คืนนั้นเซ็นเซอร์เห็นอะไร"** ปัจจุบันตอบไม่ได้เลย
เพราะไม่มีอะไรถูกบันทึกไว้นอกจากเหตุการณ์ที่ระบบตัดสินใจ "เปิด" แล้ว — สิ่งที่ระบบเห็นแต่ไม่เปิดเหตุการณ์
หายไปทันทีที่ค่าถัดไปมาถึง

สองช่องทางที่ต่างกัน ต้องไม่สับสน:

| | ใบรายงาน (ข้อ 3 ใน checkpoint) | กล่องดำ (เอกสารฉบับนี้) |
|---|---|---|
| ตอบ | "เครื่องนี้**เป็น**อะไร" | "คืนนั้น**เกิด**อะไรขึ้น" |
| รูปร่าง | สถานะ ณ ขณะนี้ ~1 หน้า | อนุกรมเวลา โตตามเวลา |
| ใช้เมื่อ | ผู้ใช้**อยู่ไกล** ส่งข้อความมาให้ | **เข้าพื้นที่ได้** ดึงไฟล์ผ่าน USB |
| ถ้าไม่มีตอนนั้น | อ่านใหม่ได้ตลอด | **หายถาวร** |

ทั้งสองต้องมี ใบรายงานคือหน้าปกที่บอกว่าตัวเลขดิบในกล่องดำมาจากเซ็นเซอร์อะไร ความละเอียดเท่าไหร่
กล่องดำที่ไม่มีหน้าปก = ตัวเลขที่แปลไม่ได้

## 1. ข้อเท็จจริงจากโค้ดที่บังคับรูปแบบการออกแบบ

ห้ามออกแบบจากจินตนาการ ทุกข้อตัดสินใจข้างล่างผูกกับข้อเท็จจริงในหัวข้อนี้

### 1.1 มีจุด fan-out จุดเดียวอยู่แล้ว

`SensorCapabilityController.kt:126-141` — ทุก source ที่เปิดใช้งานวิ่งผ่าน lambda เดียวกันนี้:

```
adapter.start(config.effectiveSamplingProfile(source)) { sample ->
    calibrationManager.recordSample(genId, sample)
    ...
    if (readiness is SensorReadiness.Ready) observationCallback?.invoke(obs)
}
```

**นี่คือจุด tap ของกล่องดำ** ไม่ต้องลงทะเบียนเซ็นเซอร์ใหม่ ไม่ต้องแตะ `ContinuousSensorAdapter`
และงานต่อ sample บนเส้นทางนี้มีอยู่แล้ว (`recordSample` + `normalize`) การเขียนลง ring จึงเป็นส่วนเพิ่มที่เล็กมาก

> ⚠️ ถ้าลงทะเบียน `registerListener` ตัวใหม่แทนการ tap: Android ให้ **rate เร็วสุดชนะแล้วทุกคนได้ตามนั้น**
> กล่องดำที่ขอ 50 Hz จะบังคับให้ยามที่ตั้งไว้ 5 Hz (`ContinuousSensorAdapter.kt:35`) กินไฟ 10 เท่า
> โดยไม่มี error และงบแบตที่คำนวณไว้ทั้งหมดผิดทันที **ห้ามทำเด็ดขาด**

### 1.2 เธรดเซ็นเซอร์มีเธรดเดียว และใช้ร่วมกับตรรกะตรวจจับ

`AndroidProtectionRuntime.kt:510` — `SensorHandlerOwner("SensorThread")` ตัวเดียว ถูกส่งต่อไปให้
`registerListener` ทุกจุด **และ** ยังรับ `postDelayed` ของ power confirmation / commissioning
(`:649`, `:1011`, `:1176`)

ผลสองข้อ:

1. **ผู้เขียน ring buffer มีเธรดเดียว** → ไม่ต้องล็อกฝั่งเขียน
2. **บล็อกเธรดนี้ = บล็อกการตรวจจับ ไม่ใช่แค่การเก็บข้อมูล** → ห้ามแตะดิสก์บนเธรดนี้เด็ดขาด

### 1.3 ต้นแบบที่ใช้งานจริงแล้ว 8.8 ชั่วโมง — และจุดที่ห้ามลอก

`EntryDriftRecorder.kt` ทำครบเกือบทุกอย่างที่กล่องดำต้องมี

| ลอกได้ | อ้างอิง |
|---|---|
| CSV มี header บอก sensor name / type / vendor / เวลาเริ่ม | `:158-170` |
| แถว `# accuracy=` แทรกตอนเซ็นเซอร์เชื่อถือไม่ได้ — ค่ากระโดดเพราะเซ็นเซอร์เพี้ยน กับเพราะมีคนขยับ หน้าตาเหมือนกัน ถ้าไม่จดไว้ แยกไม่ออกตอนสอบสวน | `:110-113` |
| เขียนไฟล์พังแล้วบริการไม่ล้ม | `:176-181` |
| แยกออกจากเส้นทางคำสั่งป้องกันโดยเจตนา (`ACTION_START_DRIFT_LOG` ไม่แตะ coordinator) | `SensorService.kt:182-193` |

| ❌ ห้ามลอก | ทำไม |
|---|---|
| `appendText(line + "\n")` **ข้างใน `onSensorChanged`** (`:104`) | เปิดไฟล์ → เขียน → ปิดไฟล์ ทุกแถว บนเธรดข้อ 1.2 · รอดมาได้เพราะทดลองตอนเครื่องนอนนิ่งและเขียนนาน ๆ ครั้ง · ที่ rate จริงจะบล็อกการส่งข้อมูลเซ็นเซอร์ = **กล่องดำที่ควรบันทึกเหตุ กลับพลาดเหตุเพราะตัวเองเขียนไฟล์อยู่** |

### 1.4 ⚠️ tap ที่ 1.1 ได้ข้อมูลเฉพาะตอนอาร์ม

`SensorCapabilityController` ปล่อยข้อมูลเฉพาะ `enabledSources` ของโหมดปัจจุบัน และเฉพาะเมื่อ `isRunning`
แปลว่า **การ tap ให้ข้อมูลเฉพาะช่วงที่อาร์มอยู่ ไม่ใช่ 24/7 ตามที่ตั้งใจไว้ตอนแรก**

| ทาง | ได้ | เสีย |
|---|---|---|
| **A. tap อย่างเดียว (เลือกอันนี้)** | ต้นทุนแบตเพิ่ม ~0 · ไม่มี listener ใหม่ · ไม่แตะสถาปัตยกรรมเดิม | บันทึกเฉพาะช่วงอาร์ม |
| B. ลงทะเบียนแยกเดินตลอด | ได้ 24/7 จริง | ติดกับดัก 1.1 · ต้อง foreground ถาวร · แจ้งเตือนค้างตลอด · กินแบต |

**เหตุผลที่เลือก A:** ช่วงที่ไม่อาร์ม = เจ้าของถือเครื่องอยู่กับตัว ซึ่งเป็นช่วงที่**มีค่าทางนิติวิทยาศาสตร์ต่ำที่สุด
แต่มีภาระความเป็นส่วนตัวสูงที่สุด** (บันทึกว่าเจ้าของเดินไปไหนบ้างทั้งวัน)
ส่วนคำถาม "แอปถูกฆ่าตอนไหน" ตอบด้วยแถว heartbeat ที่ไม่ใช้เซ็นเซอร์เลย (ข้อ 3) ซึ่งเดินได้ตลอด

## 2. สถาปัตยกรรมสามชั้น

ยืมจากกล้องวงจรปิด แต่เพิ่มชั้นที่ CCTV ทำไม่ได้ — กล้องต้องอัดพิกเซลทุกเฟรมเพราะไม่เข้าใจภาพ
**เราเข้าใจข้อมูลของเราเอง** ตอนเครื่องนอนนิ่งทั้งคืน ข้อมูลดิบ 3,600 แถว/ชม. มีสาระอยู่แถวเดียว

| ชั้น | อยู่ที่ไหน | เขียนเมื่อไหร่ | ขนาด |
|---|---|---|---|
| **A** สรุปรายนาที + heartbeat | ดิสก์ | ตลอดเวลา | **72 KB/วัน · 60 วัน = 4.3 MB** |
| **B** ring ละเอียด 2 นาที | RAM | **ไม่เขียนดิสก์เลย** | **~120 KB/source คงที่** |
| **C** คลิปเหตุการณ์ | ดิสก์ | มีเหตุ → เท B ทั้งก้อนลง | ~600 KB/ครั้ง |

ชั้น C คือหัวใจ: ได้ข้อมูล 2 นาที **ก่อน** เหตุ ไม่ใช่แค่หลังเหตุ — ตอนวิเคราะห์ คำถามคือ
"อะไรนำมาก่อน" ไม่ใช่ "เกิดอะไรหลังปลุกแล้ว"

เทียบกับการอัดดิบ 50 Hz ตลอดเวลา: **216 MB/วัน = 6.3 GB/เดือน** ซึ่งเป็นไปไม่ได้

### 2.1 เพดานหน่วยความจำเป็นค่าคงที่ ไม่ใช่เรื่องวินัย

```
❌ ArrayList<RawSensorSample>          โตได้ไม่จำกัด + 6000 อ็อบเจกต์ให้ GC ไล่เก็บทุกรอบ
✅ FloatArray(cap*3) + LongArray(cap)  จอง 2 ครั้งตอนสร้าง ตลอดชีวิตแอปไม่ alloc เพิ่มอีกเลย
```

ring 2 นาที @ 50 Hz ต่อ 1 source: `6000×3×4 B` = 70 KB + `6000×8 B` = 47 KB = **~120 KB**
ทำ 5 source ยังไม่ถึง 1 MB

ประเด็นสำคัญไม่ใช่ตัวเลข แต่คือ **มันบวมไม่ได้เชิงตรรกะ** — เป็นค่าคงที่ที่เขียนเทสต์ตรึงได้
ถ้าใช้ `ArrayList` แล้วคอย `removeFirst()` ขนาดคุมได้ก็จริง แต่เกิด-ดับอ็อบเจกต์วินาทีละ 50 ตัว
ตลอด 24 ชม. = แรงกดดัน GC = **อาการค้างเป็นจังหวะ** ปัญหาอยู่ที่อัตราการเกิด ไม่ใช่ที่ขนาด

> `RawSensorSample` (`SensorSourceAdapter.kt:6`) ถือ `values: FloatArray` เป็น reference
> ring ต้อง **คัดค่าออกมาใส่ array ของตัวเอง ห้ามเก็บตัวอ็อบเจกต์ไว้** ไม่งั้นถือ reference ค้าง 6000 ตัว

### 2.2 กฎเธรด

| เธรด | ทำได้ | ห้ามเด็ดขาด |
|---|---|---|
| `SensorThread` (ข้อ 1.2) | เขียนค่าลง array 4 ช่อง + เลื่อน cursor | เปิดไฟล์ · สร้าง String · ล็อก · log |
| เธรดเขียน (ใหม่ ตัวเดียว) | ดูดจาก ring ลงดิสก์ตามจังหวะ | บล็อก `SensorThread` |

ส่งต่อระหว่างสองเธรดผ่าน ring buffer เอง + cursor แบบ `@Volatile` — **ไม่มีคิว ไม่มี alloc**

## 3. รูปแบบไฟล์ชั้น A

1 ไฟล์ / 1 วัน · `blackbox-YYYYMMDD.csv` · **append อย่างเดียว** · ทุกบรรทัดจบด้วย `\n`

```
# blackbox v1
# device=<manufacturer>/<model> android=<sdk> app=<versionName>
# bootId=<uuid> wallAnchorMs=<epoch> elapsedAtAnchorMs=<elapsedRealtime>
# sensors=<source>:<name>:<vendor>:<resolution>:<fifoMax>;...
type,elapsedMs,wallMs,armed,mode,srcMask,samples,accMaxG,accRmsG,rotMaxDeg,lux,accuracyMin,incidents,battPct,charging
```

สามชนิดแถวในไฟล์เดียวกัน แยกด้วยคอลัมน์แรก:

| ชนิด | ความหมาย | ความถี่ |
|---|---|---|
| `M` | สรุป 1 นาที | ทุกนาที (แม้ไม่อาร์ม — คอลัมน์เซ็นเซอร์ว่าง) |
| `S` | เปลี่ยนสถานะ (arm / disarm / เปลี่ยนโหมด / เปลี่ยนตั้งค่า / accuracy เปลี่ยน) | ตามเหตุ |
| `E` | เหตุการณ์ถูกเปิด — อ้าง incident id ที่ตรงกับ `protection_incidents.bin` | ตามเหตุ |

**ทำไมแถว `M` ต้องเขียนแม้ไม่อาร์ม:** เพราะช่องว่างในลำดับเวลาคือคำตอบของข้อ 2 —
ไม่มีแถว `M` 40 นาทีตอนตี 3 ทั้งที่อาร์มอยู่ = **บันทึกว่าแอปถูกฆ่า** โดยไม่ต้องสร้างกลไกใหม่
(`HeartbeatPinger.kt:65` เต้นทุก N นาทีอยู่แล้ว แต่ไม่ได้จดลงที่ไหน)

**เวลา:** `elapsedMs` ตรงกับ `SensorEvent.timestamp` แต่รีเซ็ตตอนบูตและไม่บอกว่ากี่โมง ·
`wallMs` บอกกี่โมงแต่กระโดดตอนเครื่อง sync เวลา → **เก็บทั้งคู่ + `bootId` + หมุดเทียบใน header**
ไม่งั้นเจ้าของบอก "ตี 3" แล้วหาแถวนั้นไม่เจอ

### 3.1 ทำไมไม่ใช่ SQLite และไม่ใช่ JSON

แอปถูกฆ่ากลางอากาศได้ทุกวินาที (นั่นคือข้อ 2 ทั้งข้อ) รูปแบบไฟล์ต้องทนไฟล์ขาดกลางคัน

| | ปัญหา |
|---|---|
| SQLite | journal เสียหายตอนถูกฆ่า · ดึงออกมาเปิดดูยาก |
| JSON array | ไม่มีวงเล็บปิด = **เสียทั้งไฟล์** |
| **CSV บรรทัดต่อบรรทัด** ✅ | แถวสุดท้ายเขียนไม่จบก็ทิ้งแค่แถวนั้น ที่เหลืออ่านได้หมด · ลากเข้า Excel/pandas ได้ทันที |

> `FileIncidentRepository.kt:162-185` ใช้ temp+rename ซึ่ง**ถูกสำหรับสถานะ แต่ผิดสำหรับ log** —
> log ที่เขียนใหม่ทั้งไฟล์ทุกนาทีคือการเขียนทับตัวเองวันละพันรอบ

## 4. นโยบายเนื้อที่และการลบ

| ชั้น | เพดาน | อายุ |
|---|---|---|
| A (สรุปรายวัน) | 60 วัน | ทับของเก่าสุด |
| C (คลิปเหตุการณ์) | 64 MB | **ห้ามลบอัตโนมัติ** |

**บทเรียนจาก CCTV ที่คนตั้งค่าผิดบ่อยที่สุด:** ปล่อยให้ภาพทางเดินว่าง 30 วันทับคลิปเหตุการณ์ทิ้ง
→ คลิปเหตุการณ์ต้องมีอายุแยกและยาวกว่าเสมอ ของเราก็เหมือนกัน สรุปวันเงียบ ๆ ทิ้งได้
แต่ช่วงที่มีเหตุจริงคือของมีค่าที่สุดในระบบทั้งหมด

**ลบตอนขึ้นไฟล์วันใหม่ ไม่ใช่ตั้ง timer** — ให้การลบเกิดในจังหวะที่คาดเดาได้ ไม่แทรกกลางการบันทึก

## 5. ⚠️ ทางออกไฟล์ — แผน "เสียบ USB ดึง" ใช้กับเครื่องลูกค้าไม่ได้

`EntryDriftRecorder.kt:158` เขียนลง `context.filesDir` = `/data/data/<pkg>/files/` ซึ่งเป็น private storage
**`adb pull` เข้าไม่ถึงถ้าไม่ root** ทำได้แค่บน debug build ผ่าน `run-as`
เครื่องลูกค้าที่ลง release build มา จะดึงไม่ออก

| ทาง | ดึงยังไง | ข้อเสีย |
|---|---|---|
| **ปุ่ม export ในแอป → เขียนลง Downloads (เลือกอันนี้)** | ลากไฟล์ธรรมดา / ส่งต่อทางไหนก็ได้ | ต้องปลดล็อกเครื่องและกดเอง |
| `getExternalFilesDir()` | `adb pull /sdcard/Android/data/<pkg>/files/` | Android 11+ บาง OEM กั้น |
| `filesDir` (ปัจจุบัน) | ต้อง root | ใช้กับลูกค้าไม่ได้ |

**สรุป: เก็บที่ `filesDir` (ปลอดภัย) + ปุ่ม export** เพราะกล่องดำเป็นของที่ไม่ควรให้แอปอื่นในเครื่องอ่านได้
การเอาออกควรเป็นการกระทำที่มีเจตนา ไม่ใช่ของที่วางเปิดไว้ · บีบอัด gzip **ตอน export เท่านั้น ไม่ใช่ตอนบันทึก**

## 6. ความเป็นส่วนตัวและความน่าเชื่อถือ

กล่องดำเป็นวัตถุที่อ่อนไหวกว่าใบรายงานมาก มันคือบันทึกว่าเจ้าของอยู่ที่ไหน ขยับตอนไหน
ถ้าเครื่องถูกขโมย โจรได้ไฟล์นั้นไปด้วย

1. 🔴 **ไมค์บันทึกได้แค่ระดับเสียง (dB) ห้ามบันทึกเสียงจริง** — ข้ามเส้นนี้เมื่อไหร่เปลี่ยนหมวดกฎหมายทันที
2. **เข้ารหัสไฟล์** — `SecureKeyManager` มีอยู่แล้วในโปรเจกต์

## 7. แผนงานย่อยที่ตรวจได้จริง

### B1 — ชั้น A อย่างเดียว (ทำก่อน)

`BlackBoxWriter` + แถว `M`/`S` ทุกนาที เขียนจากเธรดเขียน **ไม่แตะเซ็นเซอร์เลยในเฟสนี้**
RAM = 0 · ดิสก์ 72 KB/วัน · ไม่มีทางทำให้แอปค้างหรือ memory บวมได้เลยเชิงโครงสร้าง

เทสต์: ไฟล์ถูกตัดตรงกลางแถวสุดท้าย → ยังอ่านแถวก่อนหน้าได้ครบ · ขึ้นวันใหม่แล้วไฟล์เกิน 60 วันถูกลบ ·
เพดานดิสก์ไม่ถูกทะลุแม้เขียนต่อเนื่อง

**ปลดล็อกทันที:** ข้อ 2 (ช่องว่างในไฟล์ = แอปถูกฆ่า) และวัตถุดิบของข้อ 1

### B2 — tap เข้าชั้น A

ต่อที่ `SensorCapabilityController.kt:126` เติมคอลัมน์สถิติต่อ source ในแถว `M`

เทสต์: **การ tap ไม่เปลี่ยน observation ที่ไหลไป `observationCallback` แม้แต่ตัวเดียว** ·
กล่องดำโยน exception แล้วการตรวจจับต้องไม่สะดุด

### B3 — ปุ่ม export

`ACTION_SEND` / เขียนลง Downloads · เทสต์: export ขณะกำลังบันทึกอยู่ ต้องไม่ได้ไฟล์ครึ่ง ๆ

### B4 — ring ชั้น B + คลิปชั้น C

**ทำหลังเจอเหตุจริงครั้งแรก** เพราะตอนนั้นจะรู้ว่า "อยากได้อะไรที่ตอนนี้ไม่มี" ซึ่งเดาตอนนี้ยังไงก็เดาผิด

เทสต์: หน่วยความจำที่ ring จองต้องเท่ากันเป๊ะหลังรับ 1 ล้านตัวอย่าง (ตรึงเป็นค่าคงที่) ·
ไม่มีการ alloc ใน path การเขียน ring

## 8. กับดักที่ต้องจำ

| แตะอะไร | ต้องระวัง |
|---|---|
| จุด tap | **ห้าม `registerListener` ตัวใหม่** — rate เร็วสุดชนะ ยามจะกินไฟเพิ่มโดยไม่มี error (ข้อ 1.1) |
| เธรดเซ็นเซอร์ | **ห้ามแตะดิสก์ / สร้าง String / ล็อก** — เธรดเดียวกับตรรกะตรวจจับ บล็อกแล้วเหตุการณ์หาย (ข้อ 1.2) |
| ring buffer | **primitive array เท่านั้น** ห้าม `ArrayList` แม้จะ `removeFirst()` — ปัญหาคือ GC ไม่ใช่ขนาด (ข้อ 2.1) |
| อายุไฟล์ | **คลิปเหตุการณ์ต้องมีอายุแยกและยาวกว่าสรุปรายวัน** ไม่งั้นวันเงียบ ๆ ทับหลักฐานทิ้ง (ข้อ 4) |
| ที่เก็บไฟล์ | `filesDir` ดึงผ่าน USB ไม่ได้บน release build — ต้องมีปุ่ม export (ข้อ 5) |
| รูปแบบไฟล์ | append อย่างเดียว · ห้าม JSON array · ห้าม temp+rename แบบ `FileIncidentRepository` (ข้อ 3.1) |
| ไมโครโฟน | **ระดับเสียงเท่านั้น ห้ามบันทึกเสียงจริง** (ข้อ 6) |

## 9. สิ่งที่ **ไม่** ทำในรอบนี้

- ไม่บันทึก 24/7 ตอนไม่อาร์ม (เหตุผลข้อ 1.4) — ทบทวนใหม่ได้ถ้าเจอเหตุที่เกิดตอนไม่อาร์มจริง
- ไม่อัดข้อมูลดิบต่อเนื่องลงดิสก์ (6.3 GB/เดือน)
- ไม่ทำใบรายงาน (ข้อ 3 ใน checkpoint) — รอเครื่องที่สอง แต่ `fifoMaxEventCount` ที่ระบุใน header
  ข้อ 3 ควรถูกเพิ่มเข้า `SensorDescriptor` พร้อมกัน เพราะเป็นตัวเลขที่ตัดสินว่ากล่องดำบนเครื่องนั้น
  "ถูก" หรือ "แพง"
