### 🔑 ต้นตอที่เจอ: โหมดวัดองศามี "2 ท่อ" อ่านเซ็นเซอร์หมุนตัวเดียวกัน

ภาพเจ้าของแสดงเหตุ **"การเคลื่อนไหวผิดปกติ" (VIBRATION)** พร้อม 30+ บรรทัด
`• รถถูกขยับ… Δ 8.12 … 24.38` ทั้งที่อยู่โหมดประตู "มุมประตู (วัดองศาได้)" สาเหตุจริง:

- **ท่อ A (ถูก):** `AndroidProtectionRuntime.registerEntryOrientationSource` มี listener เฉพาะ
  ของตัวเอง อ่าน rotation vector → `EntryDetectionPolicy` → verdict ที่มี **entry diagnostic**
  → `IncidentEngine.acceptEntry` → เหตุ `ENTRY_DOOR` ("🚪 ตรวจพบประตูเปิด")
- **ท่อ B (ผี):** `recommendedRoles(ENTRY)` ตั้ง ROTATION_VECTOR/GYROSCOPE = **PRIMARY**
  → `SensorCapabilityController` รัน adapter บน source เดียวกันนั้นด้วย → `SensorObservationNormalizer.mapKind`
  แปลง **ทุก source ที่ไม่ใช่ LIGHT → `SensorKind.VIBRATION`** → observation ดิบ (role=PRIMARY,
  **ไม่มี** entry diagnostic) → `IncidentEngine` เปิดเหตุ VIBRATION ทั่วไปคู่ขนาน

**ความขัดแย้งในโค้ด:** `signalRoles(ENTRY, DOOR_ANGLE)` ตั้งใจให้ VIBRATION = SUPPORTING
(ยืนยันเท่านั้น) แต่ role ระดับ **source** ที่ stamp มา ยังเป็น PRIMARY → engine เชื่อ source เลยเปิดเหตุ
อันเดียวนี้อธิบายครบทั้ง 3 อาการ: ผิดชนิด (VIBRATION), 30+ บรรทัดซ้ำ (rotation ยิงถี่), และคำว่า "รถ"

### 🔑 ทางแก้ (แบบ C — flag ที่ engine, สมมาตรกับ `soundAndMovementDoorWatch`)

- `IncidentEngine` เพิ่ม flag `doorAngleWatch` + helper `hostsIncident(role, kind)` — ในโหมดวัดองศา
  VIBRATION ถูกปลดจากการเป็น "host" ที่ประตูเดียว (`hasPrimaryRole`) ที่ทุก path การเปิดเหตุใช้ร่วมกัน
- ยัง**อัปเดต movement clock** (ให้ประตู corroborate) และยัง **join เหตุ ENTRY_DOOR ที่เปิดอยู่**
  ได้ (ฟีเจอร์ "ตรวจพบแรงกระแทกที่ประตู" ไม่พัง) — แค่ห้าม "เปิด/เปลี่ยนชนิด" เหตุ generic
- wire: `ProtectionCoordinator.doorAngleWatchArmed()` (= entry level เป็น DOOR_ANGLE) →
  `ProtectionRuntimeGraph` ส่งเข้า `accept()` ทั้ง 2 จุด
- **ถ้าเผลอเปลี่ยน `hostsIncident` ให้ VIBRATION เป็น host อีก บั๊กเหตุผีจะกลับมาทันที**

> `IncidentMessagePresentationFactory` (ที่ใช้ `incidentTitle`="🚨 รถอาจถูกเคลื่อนย้าย" /
> `formatEvidence`="มุมของรถ…") **ไม่มี caller ใน main** — อ้างจากเทสต์เท่านั้น ไม่ได้อยู่บนเส้นทาง
> push จริง คำว่า "รถ" ที่เหลือใน `PresentationTextCatalog` 644/776/778/781 โผล่เฉพาะ**หน้าประวัติ

**แนวทางที่เสนอ** (ยังไม่ได้ลงมือ):

1. **เลือกคำจากโหมด ไม่ใช่จากเซ็นเซอร์** — seam มีอยู่แล้ว: `IncidentMessageFormatter`
   รับ `getSnapshot: () -> ProtectionSnapshot?` อยู่แล้ว และ
   `snapshot.armedProfileSnapshot?.profile` คือโหมดที่อาร์มอยู่ ตอนนี้ getSnapshot
   ถูกใช้อ่านแค่แบตเตอรี่ (บรรทัด 75 กับ 220) เท่านั้น
2. **ทำ "สิ่งที่กำลังเฝ้า" ให้เป็นคำเดียวที่ผันตามโหมด** — VEHICLE → "รถ",
   ENTRY → "ประตู", POWER → "จุดติดตั้ง"/"ไฟเลี้ยง" แล้วให้ทุกประโยคที่ตอนนี้ hardcode
   คำว่า "รถ" ดึงคำนี้ไปใช้แทน
3. **แก้ `formatContinuation` ให้แยกชนิดเหมือน `formatTelegram`** — ตัวนี้แก้ได้ทันที
   และน่าจะปิดอาการที่เจ้าของเห็นได้เลย
4. **ใส่เทสต์ที่ทำให้กฎนี้พังไม่ได้อีก** — วนทุกข้อความที่โหมด ENTRY สร้างได้
   แล้ว assert ว่าไม่มีคำว่า "รถ" เลย (แนวเดียวกับ vocabulary ปิดของ breadcrumb:
   เปลี่ยนกฎจากสิ่งที่ต้องจำ เป็นสิ่งที่เทสต์บังคับ)

**ยังไม่ยืนยัน:** ข้อความจริงที่เจ้าของได้รับคือฉบับไหน — ยังไม่ได้ขอตัวอย่างข้อความเต็ม
ถ้าได้ข้อความจริงมาจะชี้จุดได้แม่นกว่าการไล่โค้ด

### 2. 🟡 ส่งย้อนหลังล้มแล้วไม่ลองเองจนกว่าจะมีสัญญาณจากภายนอก

รอบทดสอบที่ 2: `net:gained` ยิงตอน mobile data ต่อได้ แต่จริง ๆ ยังส่งไม่ออก →
`tg:failed:unknown` แล้ว **เงียบ** ต้องสะกิด wifi ให้เกิด `net:gained` อีกครั้งจึงส่งสำเร็จ

ถ้าปล่อยไว้ ของค้างจะรอจนกว่า heartbeat รอบถัดไป (ทุก 15 นาที) จะส่งผ่าน
แล้วค่อยถูกกวาดผ่าน hook `tg:ok` → **แย่สุด 15 นาที ไม่ใช่หายไปเลย**

แนวทาง: ให้ flush ที่ล้มตั้งเวลาลองเองอีกครั้งแบบถอยหลัง (เช่น 30 วิ → 2 นาที → 5 นาที)
แทนที่จะรอสัญญาณภายนอกอย่างเดียว

### 3. 🟡 ข้อความ "เหตุการณ์จบแล้ว" ยังใช้โควตา SMS

ถามเจ้าของไปแล้ว **ยังไม่ได้คำตอบ** — ความเห็นผม: ช่องทางที่เสียเงินควรใช้กับ
"มีเรื่องเกิดขึ้น" ไม่ใช่ "เรื่องจบแล้ว" แต่มุมกลับคือรู้ว่าจบแล้วอาจทำให้ไม่ต้องรีบกลับบ้าน

### 4. 🟢 ยังไม่ได้ทดสอบกับประตูจริง

รอบทดสอบทั้งสองรอบใช้การ **เอียงทั้งเครื่อง** ซึ่งระบบจัดเป็นคนละอย่างกับ
**ประตูที่หมุนรอบบานพับ** — สังเกตจาก `sms:denied:lowsev` ในรอบที่ 2 ที่บอกว่า
เหตุนี้ไม่เข้าเกณฑ์ "ประตูเปิด" ที่ `ceab688` เปิดทางให้ใช้ SMS

**แปลว่ากติกา SMS ที่เจ้าของเลือกไว้ (ประตูเปิด + วิกฤต) ยังไม่เคยถูกพิสูจน์กับเหตุประตูจริง**
ต้องติดเครื่องกับประตูจริงแล้วเปิดประตูเท่านั้นถึงจะรู้

### 5. 🟢 เหตุที่ค้างสถานะ "กำลังส่ง" — ปิดไปแล้วบางส่วน

`d592d58` เก็บกวาดของที่ค้างเกิน 5 นาทีแล้ว แต่ยังไม่ได้ทดสอบเคสโปรเซสถูกฆ่ากลางการส่งจริง ๆ
(ที่เจอวันนี้เป็นของเก่าที่ค้างมาจากเมื่อคืน ไม่ใช่การจำลอง)

## การตัดสินใจที่ต้องจำ

### 🔑 เพดานลองใหม่ นับเฉพาะสิ่งที่ตัวเองทำ

`IncidentRedeliveryPolicy` นับเฉพาะ attempt ที่ติดป้าย `DeliveryAttempt.REDELIVERY`
ไม่นับ attempt ที่เหตุการณ์ยิงเองตอนเกิดสด ๆ — **เพดานมีไว้กันตัวเองวนลูป จึงต้องนับตัวเอง**
ถ้าเผลอเปลี่ยนกลับไปนับทุก attempt บั๊ก `04ff3ba` จะกลับมาทันที

### 🔑 กติกาแจ้งเตือน: ยกระดับไประดับเดิม ≠ ข่าวใหม่

กฎนี้ใน `IncidentUpdateDeliveryPolicy` คือรูปทั่วไปของบั๊ก `39f4f47`
มันจะดักรูปทรงเดียวกันจากทางอื่นได้เองโดยไม่ต้องรู้ว่าทางนั้นมีอยู่
**การยกระดับที่สูงขึ้นจริง กับข้อความปิดเหตุ ไม่ถูกจำกัดด้วยอะไรทั้งสิ้น**

### 🔑 ความเงียบที่ตั้งใจ ต้องแยกออกจากความเงียบที่พัง

ทุกครั้งที่ระบบ *เลือก* จะไม่ส่ง มันจดลงกล่องดำ — `tg:denied:limited`,
`sms:denied:noconf`, `sms:denied:lowsev` เหตุผลเดียวกับที่ทำให้เริ่มงานทั้งหมดนี้:
เมื่อวานไฟล์ตอบไม่ได้ว่าคืนนั้นระบบพยายามเตือนหรือเปล่า

## วิธีทดสอบซ้ำบนเครื่องจริง (ทำได้เร็วสุดใน ~3 นาที)

```bash
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"
export PATH="$JAVA_HOME/bin:/c/Users/ASUS/AppData/Local/Android/Sdk/platform-tools:$PATH"
export MSYS_NO_PATHCONV=1

./gradlew --offline assembleDebug && adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell svc power stayon usb && adb shell input keyevent KEYCODE_WAKEUP
```
