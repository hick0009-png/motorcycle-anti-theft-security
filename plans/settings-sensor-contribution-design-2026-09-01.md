## 1. กลไกจริงที่ต้องเอามาเขียนเป็นคำอธิบาย (ตรวจจากโค้ด)

ห้ามแต่งคำโฆษณา คำอธิบายทุกบรรทัดต้องผูกกับพฤติกรรมจริงในเอนจิน

### 1.1 บทบาท 3 ระดับมีผลต่างกันจริงอย่างไร

| บทบาท | เกิดอะไรขึ้นจริง | อ้างอิง |
|---|---|---|
| **ปิด (OFF)** | ไม่ลงทะเบียน listener เลย ไม่กินแบต ไม่มีหลักฐานในข้อความแจ้งเตือน | `SensorCapabilityController.kt:93` |
| **ประกอบ (SUPPORTING)** | ทำงานและส่งหลักฐาน แต่ **เปิดเหตุการณ์เองไม่ได้** ต้องมีตัวหลักร่วมอยู่ในหน้าต่างสหสัมพันธ์ ประโยชน์คือยกระดับการจัดประเภทและเติมหลักฐาน | `IncidentEngine.kt:84,129,170` (`primaryPresent`) |
| **หลัก (PRIMARY)** | เปิดเหตุการณ์ได้ด้วยตัวเอง | `IncidentEngine.kt:506-509` |

### 1.2 ผลข้างเคียงของ "หลัก" ที่ผู้ใช้ต้องรู้ก่อนกด

1. **เครื่องไม่มีเซ็นเซอร์นั้น + ตั้งเป็นหลัก = ทั้งชุดถูกปฏิเสธ**
   `SensorCapabilityController.kt:96` ใส่ `UNAVAILABLE` issue → `status = REJECTED` → `stop()`
   ถ้าตั้งเป็น **ประกอบ** แค่เข้า `degradedSources` เฉย ๆ
   นี่คือความต่างที่ผู้ใช้มองไม่เห็นเลยในหน้าจอปัจจุบัน และเป็นกับดักที่แท้จริง
2. **ยิ่งเพิ่มตัวหลัก ยิ่ง Arm ช้า** — `ProtectionCoordinator.kt:373-383` รวบตัวหลักทั้งหมดเป็น
   `requiredPrimarySources` แล้วรอ `hasReadyPrimary()` จนครบ (มี grace window)
   เพิ่มตัวหลักหนึ่งตัว = เพิ่มตัวที่ต้องปรับเทียบเสร็จก่อนระบบจะเริ่มป้องกัน
3. **ปิดตัวหลักตัวสุดท้าย = Arm ไม่ได้** (มีไดอะล็อกเตือนอยู่แล้วที่ `SettingsScreen.kt:757`)

### 1.3 การยกระดับที่ "ตัวประกอบ" ทำได้จริง

| ประกอบเข้ามา | ร่วมกับ | ผลลัพธ์ | อ้างอิง |
|---|---|---|---|
| แสง (`AMBIENT_LIGHT`) มาก่อนการสั่นในหน้าต่างสหสัมพันธ์ | การสั่น | ยกจาก `VIBRATION`/WARNING → `TAMPER`/**CRITICAL** ("พบการงัดแงะหรือเปิดเบาะ") | `IncidentEngine.kt:151-157,163` |
| เสียง | การสั่น ห่างกัน ≤ 250 ms | ติดธง `onsetCoherent` แล้วจัดประเภทตาม `classifyAudioVibration` | `IncidentEngine.kt:88-96` |
| เสียง | ถอดสายชาร์จ | `POWER`/**CRITICAL** | `IncidentEngine.kt:99-104` |
| เสียง | ตำแหน่งเปลี่ยน | `AUDIO`/**CRITICAL** | `IncidentEngine.kt:106-111` |
| แหล่งสั่นตัวที่สอง (คนละ source) | แหล่งสั่นตัวแรก | เหตุการณ์เดียวมีหลักฐานสองแหล่ง อ่านง่ายขึ้นในข้อความ Telegram | `IncidentEngine.kt:117-118` (`it.source != observation.source`) |

### 1.4 ค่าที่แต่ละโหมดแนะนำ (จาก `recommendedSensorConfiguration`)

| Source | เฝ้ารถ (VEHICLE) | ประตู (ENTRY) | ไฟเลี้ยง (POWER) |
|---|---|---|---|
| ตรวจจับการเคลื่อนไหวหลัก | ประกอบ | ประกอบ | 🔒 ปิด |
| เซ็นเซอร์วัดความเร่ง | **หลัก** | ประกอบ | 🔒 ปิด |
| ความเร่งเชิงเส้น | ประกอบ | ประกอบ | 🔒 ปิด |
| ไจโรสโคป | ประกอบ | **หลัก** | 🔒 ปิด |
| เวกเตอร์การหมุน 3 มิติ | ประกอบ | **หลัก** | 🔒 ปิด |
| เวกเตอร์การหมุนสัมพัทธ์ | ประกอบ | **หลัก** | 🔒 ปิด |
| สนามแม่เหล็ก | ประกอบ | ประกอบ | 🔒 ปิด |
| เวกเตอร์สนามแม่เหล็กโลก | ประกอบ | ประกอบ | 🔒 ปิด |
| เซ็นเซอร์วัดแสง | **หลัก** | ประกอบ | **หลัก** (ไฟยืนยัน) |
| ระยะประชิด | ประกอบ | ประกอบ | 🔒 ปิด |

ต่างกันสองจุดเท่านั้นระหว่างเฝ้ารถกับประตู: แกนหมุนขึ้นเป็นหลัก และความเร่ง/แสงถอยเป็นประกอบ
ซึ่งอ่านจากหน้าจอปัจจุบันไม่ได้เลย

### 1.5 ⚠️ ความจริงที่หน้าจอต้องไม่ปิดบัง — โหมดประตูไม่ได้ใช้ค่าที่ตั้งตรงนี้

การตรวจ "ประตูเปิด" **ไม่วิ่งผ่าน fusion config** เลย
`AndroidProtectionRuntime.kt:1186` ลงทะเบียน `TYPE_GAME_ROTATION_VECTOR` เอง
(fallback `TYPE_ROTATION_VECTOR`) แล้วปล่อย observation ด้วย
`source = GAME_ROTATION_VECTOR, role = SensorRole.PRIMARY` **ตายตัว** (`:1241-1243`)

แปลว่าถ้าผู้ใช้ลดไจโร/เวกเตอร์การหมุนลงเป็น "ประกอบ" ในโหมดประตู
**การตรวจประตูยังทำงานเหมือนเดิมทุกประการ** สิ่งที่เปลี่ยนคือ fusion ที่วิ่งคู่ขนานเท่านั้น

ถ้าเขียนคำอธิบายว่า "ตั้งเป็นหลักเพื่อให้ตรวจประตูได้ดีขึ้น" = โกหกรอบสอง
ต้องมีหมายเหตุประจำกลุ่มการหมุนในโหมดประตูตามข้อ T7

## 2. โมเดลคำอธิบาย — โครงสร้าง ไม่ใช่ข้อความลอย

`PresentationTextCatalog` เพิ่ม projection ต่อ (โปรไฟล์ × source):

```kotlin
data class SensorContribution(
    val source: SensorSource,
    val recommendedRole: SensorRole,      // ของโปรไฟล์นี้
    val detectsTh: String,                // "ช่วยตรวจจับอะไร"
    val asPrimaryTh: String,              // ตั้งเป็นหลัก → ได้อะไร
    val asSupportingTh: String,           // ตั้งเป็นประกอบ → ได้อะไร
    val ifOffTh: String,                  // ปิด → เสียอะไร
    val costTh: String,                   // แบต / โอกาสเตือนผิด
    val caveatTh: String? = null,         // ข้อยกเว้นเฉพาะโปรไฟล์ (เช่นข้อ 1.5)
)

fun contribution(profile: ProtectionProfile, source: SensorSource): SensorContribution
```

ตัวอย่างข้อความที่ผูกกับกลไกจริง:

**ไจโรสโคป × โหมดเฝ้ารถ**
```
ช่วยตรวจจับ : การเอียงและการหมุนตัวรถ เช่น ยกขาตั้ง งัดล้อ เข็นเลี้ยว
ตั้งเป็นหลัก : เปิดเหตุการณ์ได้เองเมื่อพบการหมุนเกินเกณฑ์ แม้ยังไม่มีแรงสั่น
              แลกกับต้องรอปรับเทียบไจโรให้เสร็จก่อนเริ่มป้องกันทุกครั้ง
ตั้งเป็นประกอบ: เปิดเหตุการณ์เองไม่ได้ แต่เมื่อมาตรวัดความเร่งจับได้
              เหตุการณ์เดียวกันจะมีหลักฐานสองแหล่ง อ่านง่ายขึ้นในข้อความแจ้งเตือน
ปิด          : ประหยัดแบตที่สุด แต่การงัดที่ทำให้รถเอียงโดยไม่สั่นแรงจะหลุด
ต้นทุน       : กินแบตปานกลาง ทำงานต่อเนื่อง
```

**เซ็นเซอร์วัดแสง × โหมดเฝ้ารถ**
```
ช่วยตรวจจับ : แสงที่เปลี่ยนบริเวณจุดติดตั้ง เช่น เปิดเบาะ เปิดฝาครอบ ส่องไฟ
ตั้งเป็นหลัก : (ค่าแนะนำ) เปิดเหตุการณ์ได้เอง
ตั้งเป็นประกอบ: เมื่อแสงเปลี่ยนแล้วตามด้วยการสั่นในหน้าต่างเดียวกัน
              เหตุการณ์จะถูกยกจาก "รถอาจถูกเคลื่อนย้าย" เป็น
              "พบการงัดแงะหรือเปิดเบาะ" ระดับวิกฤต
ปิด          : การเปิดเบาะเงียบ ๆ จะไม่ถูกยกระดับ เหลือเป็นเหตุการณ์สั่นธรรมดา
ต้นทุน       : กินแบตต่ำ (on-change)
```

**ไจโรสโคป × โหมดประตู** — ต้องมี `caveatTh`
```
หมายเหตุ : การตรวจ "ประตูเปิด" ใช้เซ็นเซอร์การหมุนโดยตรงเสมอ
          ไม่ขึ้นกับบทบาทที่ตั้งตรงนี้ ค่าที่ตั้งที่นี่มีผลกับการตรวจจับ
          แบบรวมสัญญาณที่ทำงานคู่ขนานเท่านั้น
```

## 3. หน้าตา UI

### 3.1 แถวเซ็นเซอร์ในไดอะล็อก (สถานะปกติ)

```
┌────────────────────────────────────────────┐

│ ช่วยตรวจจับ: การเอียงและหมุนตัวรถ เช่น ยกขาตั้ง │

│ [ หลัก ✓ ] [ ประกอบ ] [ ปิด ]                │
│                                             │
│ ▸ เปลี่ยนบทบาทแล้วได้อะไร                     │
└────────────────────────────────────────────┘
```

### 3.2 กาง "เปลี่ยนบทบาทแล้วได้อะไร"

```
│ ● หลัก      เปิดเหตุการณ์ได้เอง · ต้องรอปรับเทียบก่อน Arm   ⭐ แนะนำ │
│ ○ ประกอบ    เปิดเองไม่ได้ · เติมหลักฐานให้เหตุการณ์เดียวกัน        │
│ ○ ปิด       ประหยัดแบตที่สุด · การเอียงเงียบ ๆ จะหลุด            │
│ ต้นทุน: กินแบตปานกลาง                                        │
```

ป้าย ⭐ แนะนำ วางที่บทบาทที่โปรไฟล์ปัจจุบันแนะนำ ไม่ใช่ค่ากลางค่าเดียวทุกโหมด
— นี่คือจุดที่ความต่างระหว่างเฝ้ารถกับประตูจะปรากฏให้ผู้ใช้เห็นเป็นครั้งแรก

### 3.3 เมื่อเครื่องไม่มีเซ็นเซอร์นั้น

```
│ เซ็นเซอร์วัดระยะประชิด          ⚠️ เครื่องนี้ไม่มีเซ็นเซอร์นี้ │
│ [ หลัก ]      ← จาง กดไม่ได้                              │
│   ตั้งเป็นหลักไม่ได้ ระบบจะปฏิเสธการตั้งค่าทั้งชุด             │
│ [ ประกอบ ] [ ปิด ✓ ]  ← ยังกดได้                          │
```

### 3.4 สรุปหัวการ์ด


## 4. แผนงานย่อย — แต่ละก้อนจบแล้วเข้าไปกดตรวจบนเครื่องได้จริง

หลักการแบ่ง: **ไม่มี task ไหนที่จบแล้วมองไม่เห็นอะไรบนหน้าจอ**
งานโดเมนล้วนถูกผูกเข้ากับชิ้น UI ที่มันไปโผล่เสมอ ทุก task จบด้วยแอปที่ build ผ่าน ติดตั้งได้ ใช้ต่อได้

เครื่องทดสอบ: Huawei INE-LX2 `JUCDU18811013149`
เส้นทางที่อ้างถึงบ่อย: **แท็บตั้งค่า → การปกป้อง → ปุ่ม "แสดงการวินิจฉัยขั้นสูง" → การ์ด "เซ็นเซอร์ขั้นสูงและบทบาทการตรวจจับ"**

---

### T1 · ล็อกเซ็นเซอร์ที่โหมดไฟเลี้ยงไม่ใช้

**ทำ:** `lockedSources/lockedCapabilities/presetSelectable` ใน `ProtectionProfilePolicy` ·
`SensorEditabilityUiModel` ใน `ProtectionUiModels` derive ใน `from()` · แบนเนอร์ล็อก ·
การ์ด 4 กลุ่มจาง + สไลเดอร์ `enabled=false` · preset เป็นชิปอ่านอย่างเดียว + ซ่อนป้าย "กำหนดเอง" ·
`semantics { disabled() }`

**ตรวจบนเครื่อง:**
1. อยู่โหมดไฟเลี้ยง → เข้าเส้นทางข้างบน → เห็นแบนเนอร์ 🔒 ข้อความอ่านชัด ไม่จาง
2. ลากสไลเดอร์ "การเคลื่อนไหว" → ตัวเลขต้องไม่ขยับ
3. แถว preset ไม่มีปุ่มสามตัวแล้ว เหลือชิป "กำหนดโดยโหมดไฟเลี้ยง" · ไม่มีป้าย "กำหนดเอง"
4. การ์ด "แสงบริเวณจุดติดตั้ง" ยัง**ลากได้ปกติ**
5. สลับไปโหมดเฝ้ารถ → ทุกอย่างกลับมาแก้ได้ครบ ไม่มีแบนเนอร์
6. เปิด TalkBack กวาดที่สไลเดอร์ที่ล็อก → ต้องได้ยิน "ปิดใช้งาน"

---

### T2 · ไดอะล็อกบทบาทแยก "ที่โหมดนี้ใช้" / "ถูกล็อก" พับได้

**ทำ:** จัดกลุ่มสองส่วนใน `AlertDialog` · หัวข้อพับ `rememberSaveable` เริ่มที่พับ ·
ปุ่มบทบาททั้งสามใส่ `enabled = false` ตอนล็อก (รวมปุ่มที่เลือกอยู่) · ชิป 🔒 + เหตุผลไม่จาง

**ตรวจบนเครื่อง:**
1. โหมดไฟเลี้ยง → "กำหนดบทบาทเซ็นเซอร์ขั้นสูง" → เห็น "เซ็นเซอร์ที่โหมดนี้ใช้ (1)" มีเซ็นเซอร์วัดแสงตัวเดียว
2. เห็นหัวข้อ "ถูกล็อกในโหมดไฟเลี้ยง (9)" พับอยู่ → กดกาง
3. กดปุ่ม "หลัก" ที่มาตรวัดความเร่ง → **ต้องไม่มีอะไรเกิดขึ้น** ไม่มี toast ไม่มีการบันทึก
4. ปิดไดอะล็อก เปิดใหม่ → สถานะพับกลับมาเป็นพับ (ค่าเริ่มต้น)
5. โหมดเฝ้ารถ → ไม่มีหัวข้อ "ถูกล็อก" เลย เห็น 10 ตัวเรียงตามเดิม

---

### T3 · ป้าย "⭐ แนะนำ" ต่อโหมด + ปุ่มคืนค่าที่แนะนำ

**ทำ:** เปิด `recommended(profile).sensorConfiguration` ให้ UI อ่าน · ป้ายบนบทบาทที่แนะนำ ·
ป้าย "ต่างจากค่าแนะนำ" บนแถวที่ผู้ใช้แก้ · ต่อปุ่มเข้า `actions.restoreRecommendedProfile` (action มีอยู่แล้ว)

**ตรวจบนเครื่อง:**
1. โหมดเฝ้ารถ → ไจโรสโคปต้องมี ⭐ ที่ "ประกอบ" · มาตรวัดความเร่งมี ⭐ ที่ "หลัก"
2. สลับไปโหมดประตู เปิดไดอะล็อกเดิม → ⭐ ของไจโรสโคป**ย้ายไปที่ "หลัก"**
   (นี่คือหลักฐานตาเปล่าว่าสองโหมดใช้เซ็นเซอร์ไม่เหมือนกันจริง)
3. เปลี่ยนไจโรเป็น "หลัก" ในโหมดเฝ้ารถ → ขึ้นป้าย "ต่างจากค่าแนะนำ"
4. กด "คืนค่าที่แนะนำของโหมดนี้" → กลับเป็น "ประกอบ" ป้ายหาย

---

### T4 · บรรทัด "ช่วยตรวจจับ" ต่อโปรไฟล์

**ทำ:** `SensorContribution` + `contribution(profile, source)` ใน `PresentationTextCatalog`
(ครบ 3 โปรไฟล์ × 10 sources) · แสดง `detectsTh` ใต้ชื่อกลุ่มในแถว

**ตรวจบนเครื่อง:**
1. ทุกแถวใน 3 โหมดมีบรรทัด "ช่วยตรวจจับ:" ไม่มีแถวไหนว่างหรือขึ้นชื่อ enum
2. เซ็นเซอร์วัดแสง โหมดเฝ้ารถ vs โหมดไฟเลี้ยง → ข้อความต้อง**ต่างกัน**
   (เฝ้ารถ = เปิดเบาะ/ส่องไฟ · ไฟเลี้ยง = ไฟยืนยันจุดติดตั้ง)
3. หมุนจอ / เข้า-ออกหน้า → ข้อความไม่หาย ไม่กระพริบ

---

### T5 · แผงเทียบผล 3 บทบาท (กางได้)

**ทำ:** แถว "▸ เปลี่ยนบทบาทแล้วได้อะไร" กางเป็น 3 บรรทัด (หลัก/ประกอบ/ปิด) + บรรทัดต้นทุน ·
⭐ วางตาม `recommendedRole` ของโปรไฟล์ปัจจุบัน

**ตรวจบนเครื่อง:**
1. กางที่ไจโรสโคป → เห็นครบ 3 บรรทัด + ต้นทุน
2. บรรทัด "หลัก" ต้องพูดถึงการรอปรับเทียบก่อน Arm
3. บรรทัด "ประกอบ" ของเซ็นเซอร์วัดแสง ต้องพูดถึงการยกระดับเป็น "พบการงัดแงะหรือเปิดเบาะ"
4. กางหลายแถวพร้อมกันได้ ไม่ดันเลย์เอาต์เพี้ยน · เลื่อนไดอะล็อกได้ปกติ

---

### T6 · สถานะฮาร์ดแวร์จริง + กันตั้ง "หลัก" ให้เซ็นเซอร์ที่ไม่มี

**ทำ:** ส่ง `availableSources: Set<SensorSource>` จาก catalog ขึ้นมาถึง UI state
(ใช้ `SensorSourceUiModel.isAvailable` ที่ประกาศไว้แล้วแต่ยังไม่ได้ต่อสาย) ·
ป้าย "⚠️ เครื่องนี้ไม่มีเซ็นเซอร์นี้" · ปุ่ม "หลัก" `enabled = false` พร้อมเหตุผล ·
ปุ่ม "ประกอบ"/"ปิด" ยังกดได้

**ตรวจบนเครื่อง:**
1. ดูว่าเครื่องทดสอบไม่มีเซ็นเซอร์ตัวไหน (เทียบกับแถบเซ็นเซอร์ในหน้าแดชบอร์ด)
2. แถวนั้นต้องมีป้ายเตือน และปุ่ม "หลัก" กดไม่ได้
3. กดปุ่ม "ประกอบ" ที่แถวเดียวกัน → บันทึกได้ปกติ ระบบไม่ปฏิเสธทั้งชุด
4. **เทสต์ถดถอยสำคัญ:** ก่อนแก้ ถ้าตั้งตัวที่ไม่มีเป็น "หลัก" ระบบจะปฏิเสธทั้งชุดเงียบ ๆ
   หลังแก้ ต้องกดไปถึงจุดนั้นไม่ได้เลย

---

### T7 · พูดความจริงเรื่องโหมดประตู (ข้อ 1.5)

**ทำ:** หมายเหตุประจำกลุ่ม "การหมุนและเอียง" เมื่อโปรไฟล์ = ENTRY
"การตรวจจับประตูใช้เซ็นเซอร์การหมุนโดยตรงเสมอ ไม่ขึ้นกับบทบาทที่ตั้งที่นี่"

**ตรวจบนเครื่อง:**
1. โหมดประตู → การ์ด "การหมุนและเอียง" มีหมายเหตุ · โหมดเฝ้ารถไม่มี
2. **ตรวจพฤติกรรมจริง:** โหมดประตู ตั้งไจโร+เวกเตอร์การหมุนเป็น "ปิด" ทั้งหมด →
   Arm → เปิดประตูจริง → **ยังต้องได้แจ้งเตือน "🚪 ตรวจพบประตูเปิด" ตามปกติ**
   (พิสูจน์ว่าหมายเหตุพูดความจริง ถ้าไม่ได้แจ้งเตือน แปลว่าเข้าใจโค้ดผิด ต้องกลับมาทบทวน)

---

### T8 · สรุปหัวการ์ด + ผลต่อการ Arm

**ทำ:** บรรทัดสรุป "หลัก N · ประกอบ N · ปิด N" ต่อโปรไฟล์ · ประโยคเตือนเรื่องรอปรับเทียบ

**ตรวจบนเครื่อง:**
1. โหมดเฝ้ารถเริ่มต้น → "หลัก 2 · ประกอบ 8 · ปิด 0"
2. เปลี่ยนไจโรเป็นหลัก → ตัวเลขขยับเป็น "หลัก 3 · ประกอบ 7"
3. กด Arm แล้วจับเวลา → ต้องรอปรับเทียบนานขึ้นกว่าตอน 2 ตัวหลักอย่างสังเกตได้

---

### T9 · (แยกเฟส) เดินสายหน้าตั้งค่าไปที่ profile overrides

**ทำ:** อ่านจาก `ProtectionProfilePolicy.resolve(state, selectedProfile)`
เขียนผ่าน `updateProfile()` แทน `SensorConfigurationRepository` ตัวกลาง

**ตรวจบนเครื่อง:**
1. โหมดเฝ้ารถ ตั้งไจโร = หลัก → สลับไปโหมดประตู → **ไจโรต้องไม่ถูกลากตามไป**
2. กลับมาโหมดเฝ้ารถ → ยังเป็นหลักอยู่
3. ฆ่าแอปแล้วเปิดใหม่ → ค่าของแต่ละโหมดยังแยกกันถูกต้อง
4. ก่อนทำ T9 ข้อ 1-3 จะพังทั้งหมด — ใช้เป็นตัวชี้วัดว่า T9 จำเป็นจริง

---

## 5. ลำดับที่แนะนำ

```
T1 → T2        (ล็อกให้ถูกก่อน — หยุดการโกหกที่ชัดที่สุด)
T3 → T4 → T5   (อธิบายว่าแต่ละตัวช่วยอะไร — ชิ้นที่เจ้าของขอ)
T6 → T7        (กับดักฮาร์ดแวร์ และความจริงของโหมดประตู)
T8             (สรุปภาพรวม)
T9             (รากของปัญหา แยก commit ชัดเจน)
```

T3 คือก้อนที่ทำให้ "ความต่างของโหมดเฝ้ารถกับโหมดประตู" ปรากฏบนหน้าจอเป็นครั้งแรก
ถ้าอยากเห็นผลเร็วที่สุดโดยไม่รอครบชุด ทำ T1 → T3 → T4 ก็พอเห็นภาพแล้ว
