# Design — กล่องดำในฐานะผู้สังเกตการณ์ทั้งระบบ (System Observer) 2026-09-04

สถานะ: **ข้อเสนอ รอเลือกเฟส** · ต่อยอดจาก [blackbox-recorder-design-2026-09-03.md](blackbox-recorder-design-2026-09-03.md) (B1–B3 ทำแล้ว)
ตัวเลขทุกตัวในเอกสารนี้วัดจากไฟล์จริงที่ดึงออกจากเครื่อง INE-LX2 วันนี้ ไม่ใช่ค่าประมาณ

## 0. นิยามใหม่ที่เจ้าของสั่ง

> "มันคือคนนอกที่เฝ้าดูเหตุการณ์ต่าง ๆ แทนเราทั้งระบบ — ไม่เกี่ยวว่าลูกค้าอยู่โหมดไหน
> เข้าถึงเซ็นเซอร์ทุกตัว เซอร์วิสทุกตัว จดบันทึกแทนเรา เมื่อผู้ใช้มีปัญหา เราอธิบายเรื่องราวให้เขาฟังได้"

เอกสารเดิมนิยามกล่องดำว่า **"คืนนั้นเซ็นเซอร์เห็นอะไร"** นิยามใหม่กว้างกว่านั้นสองขั้น:

| | เดิม (B1–B3) | ใหม่ (C) |
|---|---|---|
| ขอบเขต | เซ็นเซอร์ที่โหมดปัจจุบันเปิดใช้ | **ทุกเซ็นเซอร์ที่เครื่องมี ไม่ขึ้นกับโหมด** |
| หัวข้อที่จด | สถานะการเฝ้า | **ทุกระบบย่อย** — ส่งข้อความ, GPS, ไมค์, สิทธิ์, ระบบไฟ, การถูกฆ่า |
| ตอบคำถาม | "มีการเฝ้าอยู่จริงไหม" | **"ทำไมมันถึงเป็นแบบนั้น"** |
| ผู้อ่าน | นักพัฒนา | **ทีมซัพพอร์ตที่ต้องตอบลูกค้า** |

ความต่างที่สำคัญที่สุดคือข้อสุดท้าย — เดิมกล่องดำเป็นเครื่องมือพิสูจน์ว่าแอปยังไม่ตาย
ใหม่คือ **สำนวนคดี** ที่ทำให้ตอบลูกค้าได้ว่า "คืนนั้นระบบเห็นอะไร ทำอะไร และทำไมถึงไม่เตือนคุณ"

## 1. ช่องว่างสามข้อ ที่วัดได้จากไฟล์จริงวันนี้

ดึง `blackbox-20260903.csv` + `blackbox-20260904.csv` ออกมา 1,457 แถว ไม่มีบรรทัดขาดเลย
ชั้น A ทำงานถูกต้องทุกอย่าง แต่ชนเพดานของตัวเองสามที่

### 1.1 🔴 ข้อมูลเซ็นเซอร์เป็นตัวประกันของโหมด

เซสชัน POWER 9 ชม. 30 นาที (08:57–18:27 วันที่ 4):

```
samples = 503–504/นาที ทุกแถว 570 แถวติด  ->  8.4 Hz = เซ็นเซอร์ตัวเดียว
accMaxG / accRmsG / rotMaxDeg = ว่างทั้ง 570 แถว
```

เพราะ `lockedSources(POWER)` ปิดทุก source ยกเว้น `AMBIENT_LIGHT`
([ProtectionProfilePolicy.kt:399](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/protection/ProtectionProfilePolicy.kt))
tap อยู่ปลายทางของ detection path จึงเห็นเท่าที่ detection path เห็น

**ผลกับลูกค้า:** ลูกค้าใช้ Power Guard คาไว้ทั้งเดือน แล้ววันหนึ่งบอกว่า "รถโดนเข็นไปตอนกลางคืน"
กล่องดำตอบไม่ได้เลยว่ามีการสั่นไหม — ไม่ใช่เพราะไม่มีการสั่น แต่เพราะ **ไม่มีใครฟัง**

### 1.2 🔴 ช่องว่างในไฟล์ยังเป็นการเดา ไม่ใช่คำให้การ

45 แถว `S` ตลอด 24 ชม. — `start` 16, `arm` 11, `disarm` 6, `mode+config` 12, **`stop` = 0**

ช่องว่าง 12 จุดทุกจุดตามด้วย `start` เราจึง *เดา* ว่าเป็น `adb install` **ไฟล์ไม่ได้บอก**
กลไกที่ทั้งข้อ 2 วางอยู่บนมัน ยังไม่เคยพิสูจน์ตัวเองสักครั้งเดียว

### 1.3 🔴 ไม่มีระบบย่อยไหนถูกจดเลยนอกจากเซ็นเซอร์

โปรเจกต์มี 12 โมดูล — `telegram/` `location/` `network/` `autostart/` `telephony/` `security/` …
**ไม่มีอันไหนเขียนอะไรลงกล่องดำเลย**

คำถามที่ซัพพอร์ตเจอบ่อยที่สุดคือ *"ทำไมไม่เตือนผม"* ซึ่งคำตอบอยู่ใน `telegram/` กับ `network/`
ปัจจุบันกล่องดำเงียบสนิทเรื่องนี้

## 2. หลักการเดิมที่ห้ามทิ้ง (ทุกข้อซื้อมาด้วยบทเรียนจริง)

การขยายขอบเขตแบบซื่อ ๆ จะพังทุกข้อข้างล่างนี้ ดีไซน์ทั้งหมดในเอกสารนี้ถูกบีบด้วยตารางนี้

| หลักการ | ที่มา | ถ้าละเมิด |
|---|---|---|
| ห้าม `registerListener` เพิ่มบน source ที่ detection ใช้อยู่ | ข้อ 1.1 เอกสารเดิม | Android ให้ทุก client ที่ rate เร็วสุด → ยามวิ่ง 50 Hz กินไฟ 10 เท่า **โดยไม่มี error** |
| ห้ามแตะดิสก์ / สร้าง String / ล็อก บนเธรดเซ็นเซอร์ | ข้อ 1.2 | เธรดค้าง = โทรศัพท์ไม่ได้เฝ้า |
| ทุกชนิดแถวต้องมี **เพดานอัตรา** | ข้อ 10.2 | srcMask กระพริบ 35,000 แถว/วัน → ไฟล์เต็มใน 14 ชม. → **เงียบทั้งคืน** |
| append only · CSV บรรทัดต่อบรรทัด · fsync ทุกแถว | ข้อ 3.1 | ถูกฆ่ากลางเขียน = เสียทั้งไฟล์ |
| ชั้น A ห้ามมี token / chat id / พิกัด | ข้อ 6.3 + 10.5 | ไฟล์ไม่เข้ารหัสเพราะ**สมมติว่าไม่มีของพวกนี้** ใส่เมื่อไหร่ต้องกลับไปเข้ารหัสทันที |
| คลิปเหตุการณ์ต้องมีอายุแยกและยาวกว่าสรุปรายวัน | ข้อ 4 | วันเงียบ ๆ ทับหลักฐานทิ้ง (กับดัก CCTV คลาสสิก) |

> กฎข้อ 3 คือกฎที่ดีไซน์ใหม่นี้เสี่ยงละเมิดมากที่สุด **ทุกชนิดแถวที่เพิ่มในเอกสารนี้มีเพดานกำกับ**

## 3. โครงใหม่ห้าชั้น

ชั้น A/B/C คงเดิม เพิ่ม D กับ E ซึ่งเป็น**ชั้นที่ตอบนิยามใหม่**

| ชั้น | เนื้อหา | ที่อยู่ | จังหวะเขียน | งบ/วัน |
|---|---|---|---|---|
| **A** | สรุปรายนาที + เปลี่ยนสถานะ | ดิสก์ | ตลอดเวลา | 81 KB *(วัดจริง)* |
| **B** | ring ละเอียด 2 นาที | RAM | ไม่เขียนดิสก์ | 0 |
| **C** | คลิปเหตุการณ์ | ดิสก์ | มีเหตุ → เท B ลง | ตามเหตุ |
| **D** 🆕 | **breadcrumb ระบบย่อย** | ดิสก์ | ตามเหตุ + เพดาน | ≤ 65 KB |
| **E** 🆕 | **คำให้การตอนตาย** | ระบบปฏิบัติการ | ตอนบูตใหม่ | ~0 |

ชั้น E ไม่ใช่ไฟล์ของเรา — มันคือ ring buffer ของ Android ที่เราแค่ไปอ่าน **นี่คือชั้นที่ตอบข้อ 1.2**

## 4. C1 — ปลดข้อมูลเซ็นเซอร์ออกจากโหมด

### 4.1 กติกาที่แก้ความขัดแย้งได้

ความขัดแย้ง: นิยามใหม่บอก "ฟังทุกตัว" แต่กฎข้อ 1 ห้ามลงทะเบียนซ้ำ

**ทางออก — กล่องดำรับเฉพาะ source ที่ detection path ทิ้งไว้:**

```
สำหรับทุก SensorSource:
    ถ้า role != OFF  ->  ใช้ tap เดิม (ไม่ลงทะเบียนอะไรใหม่ ฟรี)
    ถ้า role == OFF  ->  กล่องดำลงทะเบียนเอง ที่ 5 Hz + maxReportLatencyUs = 60 วินาที
    เมื่อ role เปลี่ยนจาก OFF -> อื่น  ->  ถอนของกล่องดำออกก่อน detection ลงทะเบียน
```

กล่องดำจึงไม่มีทางแข่ง rate กับยาม เพราะ **สอง path นี้ไม่เคยถือ source เดียวกันพร้อมกัน**
ตัวควบคุมมีอยู่แล้วที่ `DefaultSensorCapabilityController` ซึ่งรู้ role ของทุก source อยู่แล้ว —
เพิ่ม adapter ชุดที่สองที่ทำงานบนส่วนเติมเต็ม (complement) ของชุดแรก

### 4.2 การหน่วง (batching) คือเหตุผลที่ทำแบบนี้ไหว

`maxReportLatencyUs` ทำให้ตัวอย่างค้างใน FIFO ของฮาร์ดแวร์ แล้วปลุก AP ครั้งเดียวต่อชุด
ที่ 5 Hz + หน่วง 60 วินาที = ปลุก **1 ครั้ง/นาที แทน 300 ครั้ง/นาที**

⚠️ **แต่ต้องเช็คก่อน:** ถ้า `fifoMaxEventCount == 0` เครื่องนั้นไม่มี FIFO การหน่วงไม่ช่วยอะไรเลย
AP จะโดนปลุกทุกตัวอย่างเหมือนเดิม เอกสารเดิมข้อ 9 ระบุไว้แล้วว่า `fifoMaxEventCount`
ควรถูกเพิ่มเข้า `SensorDescriptor` — **C1 ทำไม่ได้ถ้าไม่ทำอันนั้นก่อน**

fallback สำหรับเครื่องไม่มี FIFO: **duty cycle** — เปิดฟัง 10 วินาที ทุก 1 นาที
ได้ตัวอย่าง 1/6 ของเวลา ซึ่งพอสำหรับคอลัมน์สถิติรายนาที และกินไฟ 1/6

### 4.3 วัดค่าไฟด้วยกล่องดำเอง

มีเส้นฐานอยู่แล้วจากคืนที่ผ่านมา: คอลัมน์ `battPct` บอกว่า **21:19 → 05:05 ตกจาก 42% เหลือ 32%
= 1.3%/ชม. ตอนไม่อาร์ม** เปิด C1 แล้ววัดคืนถัดไปด้วยวิธีเดียวกัน ถ้าเกิน 2.0%/ชม. ให้ถอย

> กล่องดำวัดต้นทุนของกล่องดำเองได้ นี่คือเหตุผลที่ `battPct` อยู่ในทุกแถวตั้งแต่ B1

## 5. C2 — คำให้การตอนตาย ⭐ คุ้มที่สุด แก้น้อยที่สุด

ตั้งแต่ B1 เราสร้างกลไกทั้งหมดขึ้นมาเพื่อ *อนุมาน* ว่าแอปถูกฆ่า **Android บอกตรง ๆ ได้อยู่แล้ว**

### 5.1 `ActivityManager.getHistoricalProcessExitReasons()` — API 30+

คืน `ApplicationExitInfo` ของการตายครั้งล่าสุด ๆ พร้อม:

| ได้อะไร | มีประโยชน์ยังไงกับเรา |
|---|---|
| `getReason()` | `REASON_LOW_MEMORY` · `REASON_EXCESSIVE_RESOURCE_USAGE` · `REASON_USER_REQUESTED` · `REASON_SIGNALED` · `REASON_FREEZER` · `REASON_CRASH` · `REASON_PERMISSION_CHANGE` |
| `getDescription()` | ข้อความจากระบบ — บน OEM จีนมักบอกชื่อตัวที่สั่งฆ่า |
| `getTimestamp()` | **เวลาตายแม่นระดับมิลลิวินาที** เอามาเทียบกับแถว `M` สุดท้ายได้เป๊ะ |
| `getImportance()` | ตอนตายเราเป็น foreground service จริงหรือเปล่า |
| `getPss()` / `getRss()` | ถ้าโดนฆ่าเพราะ RAM — ตอนนั้นเรากินเท่าไหร่ |

`REASON_EXCESSIVE_RESOURCE_USAGE` คือคำตอบตรง ๆ ของ "PowerGenie ของ Huawei เล่นงานเราหรือเปล่า"

### 5.2 `setProcessStateSummary()` — จดหมายลาตาย

เขียน byte array สั้น ๆ ฝากไว้กับระบบ **ระบบเก็บให้แม้กระบวนการถูก SIGKILL**
แล้วอ่านคืนผ่าน `getProcessStateSummary()` หลังบูตใหม่

อัปเดตพร้อมแถว `M` ทุกนาที ด้วยของ 16 ไบต์:

```
[bootIdShort:4][elapsedSec:4][armed:1][profile:1][srcMask:2][incidents:2][battPct:1][flags:1]
```

**นี่คือแถวที่ไม่มีวันเขียนไม่ทัน** เพราะไม่ได้เขียนตอนตาย — เขียนล่วงหน้าไว้แล้ว

### 5.3 แถวชนิดใหม่ `X`

ตอน service เริ่ม อ่าน exit reasons ทุกตัวที่ใหม่กว่าตัวที่จดไว้ครั้งก่อน แล้วเขียน `X` หนึ่งแถวต่อการตายหนึ่งครั้ง
เพดาน: **≤ 16 แถวต่อการบูตหนึ่งครั้ง** (เท่าที่ ring ของระบบเก็บ) — ไม่มีทางท่วมไฟล์

### 5.4 ข้อจำกัดที่ต้องพูดตรง ๆ

- **API 30+** — `minSdk` เราคือ 24 ต้อง guard และเครื่องเก่ากว่านั้นไม่ได้ประโยชน์
- **เครื่องทดสอบ INE-LX2 เป็น API 28 — ทดสอบบนเครื่องนี้ไม่ได้เลย** ต้องใช้ emulator หรือเครื่องที่สอง
- OEM จีนอาจรายงานเป็น `REASON_OTHERS` / `REASON_SIGNALED` ซึ่งไม่ละเอียดอย่างที่หวัง
- **ดังนั้นชั้น A ยังต้องอยู่** ช่องว่างในแถว `M` คือหลักฐานสำรองที่ทำงานได้ทุก API และทุกยี่ห้อ

> C2 ไม่ได้แทนที่การนับช่องว่าง มันคือ**พยานปากที่สอง** ที่ยืนยันสิ่งที่ช่องว่างบอกใบ้ไว้

## 6. C3 — breadcrumb ของระบบย่อย (ชั้น D)

แนวคิดยืมจาก breadcrumb ของ crash reporter (Sentry) — ร่องรอยสั้น ๆ ที่นำไปสู่เหตุ
ต่างกันตรงที่ของเราถูกเก็บไว้แม้ไม่มีเหตุ

แถวชนิดใหม่ `D` · `note` = `<โดเมน>:<เหตุ>:<ผล>`

| โดเมน | บันทึกอะไร | เพดาน/ชม. | ตอบคำถามลูกค้าข้อไหน |
|---|---|---|---|
| `tg` | ส่ง/สำเร็จ/ล้มเหลว + คลาสของ error + หน่วงเวลา **ไม่มี token ไม่มี chat id** | 60 | "ทำไมไม่เตือนผม" |
| `net` | มี/ไม่มีเน็ต, สลับ wifi↔มือถือ | 30 | เดียวกัน |
| `sms` | fallback SMS ทำงานไหม | 20 | เดียวกัน |
| `gps` | ได้ fix / เสีย fix / **ความแม่นเป็นช่วง** ห้ามพิกัด | 30 | "ตามรถไม่เจอ" |
| `mic` | pipeline เปิด/ปิด/ล้มเหลว | 20 | "ไม่ได้ยินเสียงตัด" |
| `perm` | สิทธิ์ถูกถอน/ให้ | 10 | **สาเหตุอันดับหนึ่งของ "อยู่ ๆ ก็ไม่ทำงาน"** |
| `pwr` | เข้า/ออก doze, power save, `isIgnoringBatteryOptimizations` | 20 | "แอปหยุดเองตอนกลางคืน" |
| `therm` | `getCurrentThermalStatus()` เปลี่ยนระดับ (API 29+) | 10 | เซ็นเซอร์หยุดส่งเพราะเครื่องร้อน |
| `fgs` | foreground service start/stop, notification หาย | 20 | เดียวกับข้อ `pwr` |
| `boot` | บูตเสร็จ, autostart ทำงานไหม | 5 | "รีสตาร์ทเครื่องแล้วแอปไม่ขึ้นเอง" |

**เพดานรวม 225 แถว/ชม. = 5,400/วัน** ที่ ~45 ไบต์ = **243 KB/วัน**

⚠️ เกินงบ ต้องบีบเหลือ **60 แถว/ชม. รวมทุกโดเมน** ผ่าน token bucket ตัวเดียว
เมื่อชนเพดานให้เขียน `D,...,cap:<โดเมนที่ถูกตัด>:<จำนวน>` หนึ่งแถว **แล้วเงียบ** จนหมดชั่วโมง
→ 1,440 แถว/วัน ≈ 65 KB/วัน

> นี่คือบทเรียนข้อ 10.2 เขียนเป็นกลไก: แถวที่มีไว้บอกว่า "มีอะไรผิดปกติ"
> ต้องไม่มีวันกลายเป็นตัวที่ทำให้ทั้งกล่องดำเงียบ

## 7. C4 — ring + คลิปเหตุการณ์ และเส้นเรื่องกล้อง/ไมค์

### 7.1 สถาปัตยกรรมนี้ถูกพิสูจน์มาแล้ว

รูปแบบ "ring ใน RAM + trigger ตอนเกิดเหตุ + เททิ้งลงดิสก์" คือสิ่งเดียวกับที่ Perfetto
ใช้เป็น background tracing ของ Android ทั้งระบบ (`RING_BUFFER` mode + `STOP_TRACING` triggers)
เหตุผลตรงกันเป๊ะ: *ต้นเหตุอยู่ในอดีตอันใกล้ ตอนรู้ตัวว่าต้องอัด มันสายไปแล้ว*

แผน B4 เดิมออกแบบมาถูกแล้ว **เลื่อนขึ้นมาทำได้เลย ไม่ต้องรอเหตุจริง** เพราะนิยามใหม่
บอกชัดว่าต้องการ "2 นาทีก่อนเหตุ" ตั้งแต่ลูกค้ารายแรก

### 7.2 กล้องและไมค์ — การตัดสินใจที่ต้องทำอย่างรู้ตัว

เอกสารเดิมข้อ 6.1 ขีดเส้นแดงไว้: **ไมค์เก็บได้แค่ระดับ dB ห้ามเก็บเสียงจริง**
คำสั่งใหม่ให้รวม "กล้อง เสียง ไมค์ ทุกตัวที่เครื่องมี" ซึ่ง**กลับเส้นนั้น** ต้องกลับอย่างรู้ตัว ไม่ใช่กลับโดยบังเอิญ

| | อัดตลอดเวลา ❌ | อัดตอนมีเหตุ ✅ (เสนออันนี้) |
|---|---|---|
| ดิสก์ | เสียง 8 kHz = 1.4 GB/วัน | ~1 MB/เหตุ (เสียง 30 วิ + ภาพ 10 เฟรม) |
| ไฟ | ไมค์เปิดค้าง = แบตหมดใน 6–8 ชม. | ~0 ตอนไม่มีเหตุ |
| ถูกขโมย | โจรได้เสียงในบ้านเจ้าของทั้งเดือน | ได้เฉพาะนาทีที่มันเองก่อเหตุ |
| Play Store | ต้องประกาศ + มีเหตุผลรองรับ เสี่ยงถูกถอด | อยู่ในกรอบ security ปกติ |
| กฎหมายไทย | บันทึกเสียงต่อเนื่องในที่ส่วนบุคคล = เรื่องใหญ่ | เก็บหลักฐานตอนเกิดเหตุ = ปกติ |

**ข้อจำกัดทางเทคนิคที่ปิดทางเลือกให้เองอยู่แล้ว:** `targetSdk = 36` แล้ว Android 14+ ห้าม
สร้าง foreground service ชนิด `microphone` หรือ `camera` **ขณะแอปอยู่เบื้องหลัง** —
`CAMERA` และ `RECORD_AUDIO` เป็นสิทธิ์แบบ while-in-use ปัจจุบัน manifest ประกาศ
`specialUse|location|microphone` ไว้แล้ว แต่ **ไม่มี `camera` และไม่มีสิทธิ์ `CAMERA` เลย**

> "อัดกล้องตลอดเวลาเบื้องหลัง" จึงไม่ใช่เรื่องที่เราเลือกได้ตั้งแต่แรก ระบบปฏิบัติการปิดไว้
> ทางที่เหลือคือ trigger ตอนมีเหตุ ซึ่งบังเอิญเป็นทางที่ดีกว่าอยู่แล้ว

**ข้อเสนอ:** ring เสียงใน RAM 30 วินาที (dB + สเปกตรัมย่อ ไม่ใช่เสียงดิบ) →
เมื่อเหตุเปิด จึงเริ่มอัดเสียงจริงและถ่ายภาพนิ่ง เข้ารหัสด้วย `SecureKeyManager`
เก็บ 30 วัน ลบอัตโนมัติ · เจ้าของเปิด/ปิดได้ในตั้งค่า และ**ต้องยินยอมครั้งแรกแบบชัดเจน**

## 8. C5 — ความน่าเชื่อถือของไฟล์ (hash chain)

แต่ละแถวพก hash ของแถวก่อนหน้า ตามแผน B5 เดิม แก้ทีหลังแล้วตรวจจับได้

จากงานวิจัย: hash chain ตรวจสอบเป็น O(n) ส่วน history tree แบบ Merkle (Crosby & Wallach)
ได้ O(log n) และเป็นฐานของ Certificate Transparency

**เราเลือก hash chain** เพราะไฟล์วันละ ~1,400 แถว ไล่ทั้งไฟล์ใช้เวลาไม่ถึงวินาที
Merkle ได้เปรียบตอนหลักล้านแถวซึ่งเราไม่มีวันไปถึง — **และมันทำลายคุณสมบัติที่เลือก CSV มาตั้งแต่แรก**
คือเปิดด้วย Excel/pandas ได้ทันที

⚠️ ย้ำสิ่งที่เอกสารเดิมพูดไว้: กุญแจอยู่ในเครื่อง นี่คือ tamper-**evident** ไม่ใช่ tamper-**proof**
กันการแก้แบบง่าย ๆ ได้ กันคนที่ถอดกุญแจออกมาไม่ได้

## 9. C6 — เครื่องมืออ่าน คือส่วนหนึ่งของระบบ ไม่ใช่ของแถม

วันนี้ 1,457 แถวกลายเป็นเรื่องเล่าได้ เพราะเขียนสคริปต์ parse ขึ้นมาสด ๆ
**ครั้งหน้าที่ลูกค้าโทรมา คนที่รับสายจะไม่เขียนสคริปต์เป็น**

ต้องมี reader ที่ ship มาด้วย และแสดงสิ่งที่ทีมซัพพอร์ตต้องการจริง:

1. **ไทม์ไลน์** — แถว `S`/`E`/`X`/`D` เรียงเวลา แปลเป็นภาษาคน
2. **แผนที่ช่องว่าง** — ทุกช่วงที่ไม่มีแถว `M` พร้อมคำตัดสิน: ปิดปกติ / ถูกฆ่า (+เหตุผลจาก `X`) / ไม่ทราบ
3. **ตารางเซสชันอาร์ม** — โหมด, ระยะเวลา, จำนวนเหตุ, สถิติเซ็นเซอร์สูงสุด
4. **ตัวตรวจความขัดแย้ง** — เช่นที่จับได้วันนี้: `srcMask` บอกว่าเฝ้าอยู่ แต่ `samples` บอกว่ามีเซ็นเซอร์ตัวเดียว

ข้อ 4 คือของที่มีค่าที่สุดและเกือบไม่มีใครทำ — **ให้ไฟล์ตรวจสอบตัวเองว่ามันขัดแย้งกันเองตรงไหน**

## 10. ลำดับงานที่แนะนำ

| เฟส | งาน | แรง | ผล | ต้องมีก่อน |
|---|---|---|---|---|
| **C2** | exit reasons + state summary + แถว `X` | **เล็ก** | **ใหญ่ที่สุด** — ปิดข้อ 1.2 | — |
| **C0** | แก้ `srcMask` โกหก (`getEffectiveHealth` คืน HEALTHY ให้ role OFF) | จิ๋ว | ไฟล์เลิกขัดแย้งตัวเอง | — |
| **C6** | reader + ตัวตรวจความขัดแย้ง | กลาง | ทีมซัพพอร์ตใช้งานได้จริง | C2 |
| **C3** | breadcrumb ชั้น D + token bucket | กลาง | ตอบ "ทำไมไม่เตือนผม" | C6 |
| **C1** | เซ็นเซอร์ไม่ขึ้นกับโหมด | **ใหญ่** | ปิดข้อ 1.1 | `fifoMaxEventCount` |
| **C4** | ring + คลิป + เสียง/ภาพตอนมีเหตุ | ใหญ่ | หลักฐานตัวจริง | C1 + ตัดสินเรื่องความยินยอม |
| **C5** | hash chain | เล็ก | ใช้อ้างกับตำรวจ/ประกันได้ | เมื่อมีความจำเป็น |

**เริ่มที่ C2 + C0** — สองอันรวมกันแตะโค้ดไม่กี่สิบบรรทัด แต่เปลี่ยนกล่องดำจาก
"ไฟล์ที่ต้องตีความ" เป็น "ไฟล์ที่ให้การ"

## 11. สิ่งที่ **ไม่** ทำ

- ❌ ไม่อัดเสียง/ภาพต่อเนื่อง — ระบบปฏิบัติการห้าม, ไฟไม่พอ, และโจรจะได้ไฟล์นั้นไป
- ❌ ไม่ย้ายไป SQLite แม้ชนิดแถวจะเยอะขึ้น — เหตุผลข้อ 3.1 เดิมยังจริงทุกตัวอักษร
- ❌ ไม่เอาพิกัดเข้าชั้น A — จะทำให้ต้องกลับไปเข้ารหัสทั้งไฟล์ (ข้อ 10.5)
- ❌ ไม่ส่งกล่องดำขึ้นเซิร์ฟเวอร์อัตโนมัติ — การเอาไฟล์ออกต้องเป็นการกระทำที่มีเจตนาของเจ้าของเสมอ
