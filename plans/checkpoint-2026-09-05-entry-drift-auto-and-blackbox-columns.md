## งานที่ 1 — การไหลของมุมประตู (`8352226`, `4abe44a`)

### ปัญหาที่เจอ

`EntryDriftSampler.measurement()` หารมุมสูงสุดด้วยเวลาที่ผ่านไป เจ้าของหยิบเครื่องตอน 05:00
เพื่อเสียบสาย → มุมพุ่ง 178° → 20.55 °/ชม. → ถึงเกณฑ์ใน 0.73 ชม. → `Unusable`
**8 ชั่วโมงที่ดีถูกล้างด้วย 6 นาที** และไม่มีอะไรในไฟล์หรือบนการ์ดบอกว่าทำไม

### เพดานที่ calibrate จากข้อมูลจริง ไม่ได้เดา

| | อัตราต่อ 1 ช่วงแถว (10 วิ) |
|---|---|
| นิ่งจริง 2,843 ช่วง — สูงสุด | 0.035 °/s |
| ถูกหยิบ — ก้าวแรก | 0.136 °/s |
| ถูกหยิบ — สูงสุด | 17.2 °/s |
| **เพดานที่เลือก** | **0.1 °/s** |

ยังสูงกว่า drift ของเครื่องที่แย่จนใช้ไม่ได้ (15° ใน 2 ชม. = 0.002 °/s) **50 เท่า**
ไม่มีอะไรที่ควรอยู่ในผลวัดข้ามเพดานนี้ได้

### กลไก

- ตัดสินทุก **ช่วงแถว** ไม่ใช่ทุก sample — ที่ game rate ระยะห่างคือมิลลิวินาที
  noise ธรรมดาคิดเป็น °/s แล้วมหาศาล ช่วงแถวคือหน้าต่างที่เพดานถูก calibrate มา
- ข้ามเพดาน = ปิดช่วงวัด **ที่ checkpoint ก่อนหน้า** ไม่ใช่ที่จุดที่ตรวจเจอ
  (10 วินาทีนั้นปนกับการเคลื่อนไหวไปแล้ว แยกไม่ออก)
- เปิดช่วงใหม่ด้วย baseline ใหม่ — เครื่องถูกวางที่อื่น offset คงที่นั้นก็ไม่ใช่ drift
- **ช่วงสะอาดที่ยาวที่สุดชนะ** คืนที่ไม่มีใครแตะ = ช่วงเดียว ไม่เสียอะไรเลย
- แถวใน CSV **ยังดิบ** — ไฟล์คือหลักฐาน สิ่งที่เกิดขึ้นต้องอ่านได้
  กรองเฉพาะ `measurement()` และมันรายงาน **ชั่วโมงที่วัดจริง** ไม่ใช่ชั่วโมงที่เปิดเครื่องอัด
  (สำคัญเพราะ `save()` เก็บอันที่ยาวกว่า — duration ที่พองจะบังผลวัดซื่อสัตย์ทุกอันหลังจากนั้น)

### วัดเองระหว่างเฝ้า (`EntryDriftAutoMeasure`)

เกาะ `entryOrientationSamples()` ที่ประกาศไว้ใน `ProtectionRuntime` ตั้งแต่รอบก่อนแต่ **ไม่เคยมีใคร subscribe**
โหมดประตูตอนอาร์มลงทะเบียนเซ็นเซอร์ตัวเดียวกัน rate เดียวกันอยู่แล้ว → ไม่มี listener ที่สอง
ไม่กินแบตเพิ่ม ไม่ต้องให้เจ้าของตัดสินใจอะไร

`ProfileDeviceSupportPolicy` ยอมให้เครื่องที่ยังไม่มีผลวัดอาร์มได้อยู่แล้ว (`f4fa252`)
**คืนแรกนั้นเองคือคืนที่ผลิตผลวัด**

กันสองทางที่จะได้ตัวเลขที่ไม่เคยวัดจริง:
- เซ็นเซอร์ค้าง → ส่งค่าเดิมซ้ำ = หน้าตาเหมือนเครื่องนิ่งสมบูรณ์แบบ → ตัดด้วย `EntryOrientationSample.fresh`
- เว้นช่วง > 60 วิ = คนละเซสชัน คนละคืน คนละที่ → เปิดช่วงใหม่ ไม่รับมรดกชั่วโมงที่ไม่มีใครเฝ้า

เขียนลง store ทุก 10 นาทีระหว่างช่วงวัดโตขึ้น **ไม่รอจบเซสชัน** — โปรเซสนี้ถูกฆ่าได้ตลอด
และ `save()` เก็บอันยาวกว่าอยู่แล้ว การเขียนซ้ำจึงฟรี

## งานที่ 2 — คอลัมน์แบตของกล่องดำ (`3180795`)

### ต้นเหตุ

`PowerThermalMonitor` ลงทะเบียน `ACTION_BATTERY_CHANGED` ใน `startPowerStatusMonitoring()`
และ **ผู้เรียกเพียงรายเดียวคือ `ProtectionViewModel`** — คือหน้า UI

เครื่องที่ไม่ได้อาร์มและไม่ได้เปิดแอปจึงไม่มีอะไร refresh แบตเลย `recordSensorSample`
เก็บค่าล่าสุดที่เคยเห็นไว้ (ถูกแล้วสำหรับ snapshot ที่ผู้อ่านต้องการคำตอบล่าสุด)

**แต่ไฟล์ไม่ใช่ผู้อ่านแบบนั้น** ทุกแถวคือคำกล่าวอ้างเกี่ยวกับนาทีนั้น ค่าเดิมที่ถูกเขียนซ้ำ
หลังต้นทางเงียบไปแล้ว = การยืนยันว่านาทีนั้นวัดแบตแล้วและมันไม่ขยับ

> ผู้อ่านที่กำลังหาสาเหตุว่าเครื่องตายตอนกลางคืนเพราะอะไร เห็น 100% เรียบ ๆ แล้วตัดแบตออกจากความเป็นไปได้
> ถ้าเว้นว่าง เขาจะไปถามต่อ **ตัวเลขที่มั่นใจแต่ผิด แพงกว่าช่องว่าง**

### วิธีแก้

Gate ด้วย source mask → สองคอลัมน์ขัดกันเองไม่ได้ เป็นการซ่อมแบบเดียวกับที่ `sourceMaskOf` เคยได้รับ
และ **หยุดที่ตัวบันทึกเหมือนกัน** — `ProtectionSnapshot.batteryLevelPercent` ถูกอ่านโดย arming,
ข้อความแจ้งเตือน และ UI ซึ่งไม่มีใครอยากได้ค่าที่หายไปทุกครั้งที่ monitor อยู่ระหว่างลงทะเบียน

**ต้นเหตุจงใจปล่อยไว้** — power monitoring ถูกถือครองโดย view model เป็นปัญหา lifecycle
และการย้ายมันไปแตะ arming

### ยืนยันบนเครื่อง

```
บิลด์เก่า:  S,...,start,0      ← battPct=96 charging=1  (ค่าที่ไม่มีใครอ่านอยู่)
บิลด์ใหม่:  S,...,0,,,start,0  ← เว้นว่างทั้งคู่
```

รอบที่แล้วค้างไว้ว่า "ยังไม่เคยเห็น broadcast จริง · `adb` ส่ง protected broadcast ไม่ได้"

**วิธีที่ใช้ได้:** `adb shell service call alarm 3 s16 <Zone>` (shell มีสิทธิ์ SET_TIME_ZONE
ส่วน `setprop persist.sys.timezone` ถูกปฏิเสธ ต้อง root)

```
T,151706186,1788562708109,0,-,0,,,,,,,0,,,clock:tz:0,0    ← เปลี่ยนไป Asia/Tokyo
T,151734945,1788562736868,0,-,0,,,,,,,0,,,clock:tz:0,0    ← เปลี่ยนกลับ Asia/Bangkok
```

`:0` ท้ายโน้ตคือ drift วินาที — **ถูกต้อง** เพราะเปลี่ยน timezone ไม่ขยับ epoch clock
ขยับแค่วิธีแสดงผล เพดาน 12 แถว/ชม. ไม่ถูกแตะ · timezone คืนค่าแล้ว

## บทเรียนของรอบนี้

**ค่าคงที่ที่ calibrate จากข้อมูลจริง อธิบายตัวเองได้ ค่าที่เดาไม่ได้** — เพดาน 0.1 °/s
มีตัวเลขสองฝั่งกำกับ (0.035 กับ 0.136) และมีระยะห่างจากขอบเขตทางฟิสิกส์ (50×) เขียนกำกับไว้
ค่าที่เดามาจะไม่มีอะไรให้คนอ่านโค้ดปีหน้าตรวจสอบเลย

**บั๊กพันธุ์เดียวกันซ้ำสามที่แล้ว** — `srcMask` (`f063c5b`), `failureCount` (`326f4b4`),
คอลัมน์แบต (`3180795`) ทั้งหมดคือ *คอลัมน์ที่อ้างสิ่งที่ไม่ได้วัดในนาทีนั้น*
ควรตั้งเป็นกฎตรวจก่อนเพิ่มคอลัมน์ใหม่ทุกครั้ง: **ถ้าต้นทางเงียบ คอลัมน์นี้เว้นว่างหรือโกหก?**

**ปุ่มที่มีอยู่แล้วแต่มองไม่เห็น เท่ากับไม่มี** — ผมสรุปผิดกลางทางว่า "ไม่มีทางล้างผลวัดเดิม"
เพราะ grep `.clear()` ไม่เจอ ทั้งที่ `EntryDriftMeasurementCard` มีปุ่ม "ลบผลวัดเดิม แล้ววัดใหม่"
ต่อถึง `store.clear()` จริง — มันแค่ซ่อนตอนกำลังบันทึกอยู่ ซึ่งเป็นตอนเดียวกับที่เจ้าของ
เพิ่งรู้ตัวว่าทำการวัดเสีย **เงื่อนไขการแสดงปุ่มควรทบทวน**
