# Design — C3 breadcrumb ชั้น D: ตอบ "ทำไมไม่เตือนผม" (2026-09-05)

สถานะ: **§12 เคาะแล้ว · D0 กำลังทำ** · ต่อยอดจาก [blackbox-system-observer-2026-09-04.md](blackbox-system-observer-2026-09-04.md) §6
ข้อกำหนดก่อนหน้า **C6 (reader) ทำแล้ว** (`a0bb08d`) → C3 เริ่มได้
ตัวเลขทุกตัวในเอกสารนี้วัดจากไฟล์จริงบน INE-LX2 ไม่ใช่ค่าประมาณ

---

## 1. คำถามที่เอกสารนี้ต้องทำให้ตอบได้

เจ้าของโทรมาบอกว่า **"เมื่อคืนรถโดนงัด แอปไม่เตือนผมเลย"**

วันนี้กล่องดำตอบได้แค่ว่าแอปยังไม่ตาย (แถว `M` ต่อเนื่อง) และเซ็นเซอร์เห็นอะไร
แต่ตอบไม่ได้เลยว่า **ระหว่าง "เซ็นเซอร์เห็น" กับ "โทรศัพท์เจ้าของสั่น" มันขาดตรงไหน**

ช่วงที่มืดสนิทมีอย่างน้อยเจ็ดจุด:

```
เซ็นเซอร์เห็น → เปิดเหตุ → ประกอบข้อความ → มีเน็ตไหม → ส่ง Telegram
                                              ↓ ไม่มี
                                          fallback SMS → ส่งได้ไหม
```

ทุกจุดล้มเหลวเงียบได้หมด และไม่มีจุดไหนทิ้งร่องรอยไว้ในไฟล์เลย

**ชั้น D คือร่องรอยของช่วงนั้น** แนวคิดยืมจาก breadcrumb ของ crash reporter
ต่างตรงที่ของเรา **เก็บไว้แม้ไม่มีเหตุ** เพราะคำถาม "ทำไมไม่เตือน" มาถึงเราหลังจาก
สิ่งที่ควรเกิดไม่ได้เกิดไปแล้ว — ไม่มี crash ให้แนบ breadcrumb ไปด้วย

---

## 2. รูปแบบแถว

แถวชนิดใหม่ `D` · **คอลัมน์เดิมทั้ง 17 ตัว ไม่เพิ่มคอลัมน์**

```
D,elapsedMs,wallMs,armed,mode,srcMask,,,,,,,incidents,battPct,charging,<note>,writeFails
```

- คอลัมน์สถานะ (`armed`/`mode`/`srcMask`/`incidents`) **เติมจาก `lastState` เหมือนแถวอื่น**
  ไม่ใช่ของแถม — "Telegram ล้มเหลวตอนอาร์มอยู่ในโหมดไหน มีเหตุค้างกี่เหตุ" คือคำถามถัดไปเสมอ
- คอลัมน์เซ็นเซอร์เว้นว่าง
- คอลัมน์แบต ตามกฎใหม่ของ `3180795` (เว้นว่างถ้า POWER ไม่อยู่ใน mask)

### note = `<domain>:<event>:<detail>` (+ `xN` ถ้าถูกยุบ)

```
D,...,tg:send:http429,0
D,...,net:lost:wifi x7,0
D,...,perm:revoked:location,0
D,...,cap:net:23,0
```

**เพิ่ม `BlackBoxRowType.BREADCRUMB("D")`** — `BlackBoxCsv.parse()` คืน `null` ให้ชนิดที่ไม่รู้จักอยู่แล้ว
แอปเวอร์ชันเก่าที่อ่านไฟล์ใหม่จะข้ามแถว `D` ไปเงียบ ๆ ไม่พังทั้งไฟล์ — เหมือนที่ v1 อ่าน v2 ได้

## 3. ⚠️ ช่องโหว่ในสเปกเดิม: ถังเดียวทำให้เสียงดังกลบเสียงสำคัญ

สเปกเดิม §6 กำหนด **token bucket ตัวเดียว 60 แถว/ชม. รวมทุกโดเมน**

นั่นแปลว่าเน็ตที่กระพริบ (เพดานเดิมของมันเอง 30/ชม.) บวก Telegram ที่ retry (60/ชม.)
**กินงบทั้งชั่วโมงได้ก่อนที่ `perm` จะได้เขียนสักแถว** — ทั้งที่เอกสารเดิมเขียนเองว่า
`perm` คือ *"สาเหตุอันดับหนึ่งของ 'อยู่ ๆ ก็ไม่ทำงาน'"*

> นี่คือบทเรียนข้อ 10.2 เวอร์ชันที่ลึกกว่าเดิม: ไม่พอที่แถวเตือนจะไม่ทำให้ทั้งไฟล์เงียบ
> **มันต้องไม่ทำให้แถวเตือนที่สำคัญกว่าเงียบด้วย**

### วิธีแก้: โควตาที่ยึดไม่ได้ + สระกลาง

แต่ละโดเมนมีโควตาขั้นต่ำต่อชั่วโมงที่โดเมนอื่นแย่งไม่ได้ ที่เหลือเป็นสระกลางใครมาก่อนได้ก่อน

| โดเมน | บันทึกอะไร | โควตายึดไม่ได้ | ตอบคำถามข้อไหน |
|---|---|---|---|
| `tg` | ส่ง/สำเร็จ/ล้มเหลว + คลาสของ error + หน่วง | 6 | **ทำไมไม่เตือนผม** |
| `net` | มี/ไม่มีเน็ต, สลับ wifi↔มือถือ | 4 | เดียวกัน |
| `sms` | fallback SMS ทำงานไหม | 3 | เดียวกัน |
| `perm` | สิทธิ์ถูกถอน/ให้ | 4 | **อยู่ ๆ ก็ไม่ทำงาน** |
| `pwr` | เข้า/ออก doze, power save, battery optimization | 4 | แอปหยุดเองตอนกลางคืน |
| `fgs` | foreground service start/stop, notification หาย | 4 | เดียวกัน |
| `gps` | ได้/เสีย fix, **ความแม่นเป็นช่วง** | 4 | ตามรถไม่เจอ |
| `mic` | pipeline เปิด/ปิด/ล้มเหลว | 3 | ไม่ได้ยินเสียงตัด |
| `therm` | `getCurrentThermalStatus()` เปลี่ยนระดับ (API 29+) | 2 | เซ็นเซอร์หยุดเพราะเครื่องร้อน |
| `boot` | บูตเสร็จ, autostart ทำงานไหม | 2 | รีสตาร์ทแล้วแอปไม่ขึ้น |
| **สระกลาง** | | **24** | |
| **รวม** | | **60/ชม.** | |

ลำดับการเบิก: **โควตาตัวเองก่อน → สระกลาง → ถูกตัด**
เน็ตกระพริบจึงกินโควตาตัวเอง 4 + สระกลางที่เหลือ แต่ `perm` มี 4 แถวรออยู่เสมอ

### แถว cap

ชนเพดานแล้ว **เงียบจนหมดชั่วโมง** แล้วเขียนสรุปตอนชั่วโมงใหม่เริ่ม:

```
D,...,cap:net:23,0        ← ชั่วโมงที่แล้ว net ถูกตัดไป 23 แถว
```

เขียนตอนชั่วโมงหมุน ไม่ใช่ตอนชน — **ตามกลไกเดียวกับแถว `T`** (`writeTimeRow`) เป๊ะ ๆ
เหตุผลสองข้อ: ตอนชนคือตอนที่ไม่มี token จะจ่ายให้แถว cap อยู่แล้ว และตอนชั่วโมงหมุน
ตัวเลขนิ่งแล้ว · หนึ่งแถวต่อโดเมนที่ถูกตัด ไม่ใช่หนึ่งแถวรวม — ผู้อ่านต้องรู้ว่า *อะไร* หายไป

## 4. ยุบก่อนถึงถัง (coalescing)

เน็ตกระพริบ 40 ครั้งใน 3 นาทีไม่ควรกิน 40 slot และไม่ควรกิน 4 slot แล้วปิดปาก
มันควรกิน **1 slot** แล้วบอกว่าเกิด 40 ครั้ง

ก่อนเข้าถัง: ถ้า `<domain>:<event>:<detail>` ซ้ำกับแถวก่อนหน้าของโดเมนนั้น **ภายใน 60 วินาที**
ให้เพิ่มตัวนับแทนการเขียนแถวใหม่ แล้วเขียนออกเมื่อหน้าต่างปิดหรือเมื่อ detail เปลี่ยน:

```
net:lost:wifi x40
```

ได้ทั้งการประหยัดและข้อมูลที่ละเอียดกว่าเดิม — **ความถี่ของการกระพริบคือตัวอาการเอง**
การจำกัดอัตราเฉย ๆ จะทิ้งข้อมูลนั้นไป

## 5. ความเป็นส่วนตัวต้องบังคับด้วยชนิดข้อมูล ไม่ใช่ด้วยกฎในเอกสาร

สเปกเดิมเขียนว่า *"ไม่มี token ไม่มี chat id"* และ *"ห้ามพิกัด"* — นั่นคือกฎที่คนเขียนโค้ด
คนถัดไปมองไม่เห็น ถ้า API รับ `String` เมื่อไหร่ก็มีคนใส่ข้อความ error ดิบลงไปเมื่อนั้น
และข้อความ error ของ Telegram **มี chat id อยู่ในนั้น**

> ไฟล์อยู่ใน private storage จริง แต่ `BlackBoxState` เขียนไว้เองแล้วว่า
> *เครื่องที่ถูกขโมยคือเครื่องที่ private storage อยู่ในมือคนอื่น*

**ข้อเสนอ: ไม่มี `String` ในเส้นทางเข้าเลย**

```kotlin
enum class BreadcrumbDomain(val code: String) { TELEGRAM("tg"), NET("net"), PERM("perm"), … }
enum class BreadcrumbEvent(val code: String)  { SEND("send"), OK("ok"), LOST("lost"), REVOKED("revoked"), … }

/** ค่าที่อนุญาตให้ปรากฏในไฟล์ ทั้งหมด ปิดรายการ */
sealed interface BreadcrumbDetail {
    data class Code(val value: BreadcrumbCode) : BreadcrumbDetail   // http429, timeout, wifi, mobile, location…
    data class Bucket(val value: BreadcrumbBucket) : BreadcrumbDetail // lt10 / 10_50 / gt50 …
}
```

ผลที่ได้:
- **พิกัดเขียนลงไปไม่ได้** เพราะไม่มีชนิดข้อมูลไหนรับตัวเลขทศนิยม
- ความแม่นของ GPS เข้าไปเป็น **ช่วง** (`gps:fix:lt10`) ไม่ใช่เมตร
- error ของ Telegram เข้าไปเป็น **คลาส** (`tg:send:http429`) ไม่ใช่ข้อความ
- หน่วงเวลาเข้าไปเป็น **ช่วง** (`tg:ok:lt2s`) ไม่ใช่มิลลิวินาที

การรีวิวโค้ดเปลี่ยนจาก "อ่านทุก call site ว่ามีใครใส่ข้อมูลอ่อนไหวไหม"
เป็น "อ่าน enum เดียวว่ามีสมาชิกไหนไม่ควรอยู่" — **ตรวจได้จริงและตรวจครั้งเดียว**

### ห้ามเด็ดขาด (เขียนไว้ให้ชัดว่าอะไรบ้าง)

พิกัด · chat id · bot token · เบอร์โทร · SSID · เนื้อความข้อความ · path ของไฟล์ · IMEI/serial

## 6. ทางเข้าต้องไม่ทำให้ผู้เรียกช้า

breadcrumb ถูกทิ้งจากเธรดของระบบย่อยอื่น — callback ของ ConnectivityManager,
coroutine ของ Telegram, BroadcastReceiver ของสิทธิ์ **การเขียนดิสก์ตรงนั้นรับไม่ได้**
โดยเฉพาะเมื่อบางตัวใช้เธรดเดียวกับ detection

```
ผู้เรียก → offer() ไม่บล็อก → คิวขนาดจำกัด (128) → เธรดเขียนของกล่องดำเดิม → ดิสก์
```

- คิวเต็ม = **นับแล้วปล่อยผ่าน** ห้ามบล็อก ห้าม throw
- ตัวนับที่ตกหล่นต้องไปถึงไฟล์ — `D,...,drop:queue:<n>` เขียนตอนชั่วโมงหมุนพร้อมแถว cap

> **บทเรียนของ `failureCount` (`326f4b4`) เขียนเป็นกลไก:** ตัวนับที่ไม่มีใครอ่าน เท่ากับไม่มี
> คิวที่ล้นเงียบ ๆ จะสร้างช่องว่างที่อ่านเหมือน "ไม่มีอะไรเกิดขึ้น" ซึ่งเป็นคำตอบที่ผิดที่สุด

ใช้เธรดเขียนเดิมของ `BlackBoxWriter` — มันมี lock อยู่แล้ว, `append` เปิด-เขียน-ปิดต่อแถว
และการ export ก็ถือ lock เดียวกัน **ไม่เพิ่มเธรด ไม่เพิ่ม lock**

## 7. งบดิสก์ วัดจากแถวจริง

แถว `T` ที่เพิ่งเกิดจริงเมื่อเช้านี้ยาว **55 ไบต์**:

```
T,151706186,1788562708109,0,-,0,,,,,,,0,,,clock:tz:0,0
```

แถว `D` โครงเดียวกัน note ยาวใกล้เคียง → **~55 ไบต์**

| | ต่อวัน | × 60 วัน |
|---|---|---|
| ชั้น A (วัดจริง `blackbox-20260904.csv`) | 81 KB | 4.9 MB |
| ชั้น D (60/ชม. × 24 × 55 B) | 79 KB | 4.7 MB |
| **รวม** | **160 KB** | **9.6 MB** |

- `MAX_DIRECTORY_BYTES` = 8 MB → **ต้องขยับเป็น 16 MB**
- `MAX_FILE_BYTES` = 1 MB/วัน → 160 KB คือ **16%** ยังพอมาก
- `RETENTION_DAYS` = 60 → ไม่ต้องแตะ

⚠️ 79 KB/วันคือ **กรณีชนเพดานตลอด 24 ชม.** ซึ่งไม่ใช่เครื่องปกติ
เครื่องที่สุขภาพดีจะเขียนไม่กี่สิบแถวต่อวัน — งบนี้คือเพดาน ไม่ใช่ค่าที่คาด

## 8. ผลตอบแทนอยู่ที่ตัวตรวจความขัดแย้ง ไม่ใช่ที่ไทม์ไลน์

C6 (`BlackBoxReportBuilder`) มี `BlackBoxContradiction` อยู่แล้ว — **จุดที่ไฟล์ขัดแย้งกันเอง**
แถว `D` ทำให้มันตอบคำถามของเจ้าของได้ตรง ๆ ไม่ใช่แค่เพิ่มบรรทัดในไทม์ไลน์

กฎที่เพิ่มได้ทันทีเมื่อมีชั้น D:

| กฎ | อ่านออกมาเป็น |
|---|---|
| `incidents` เพิ่ม แต่ไม่มี `tg:*:ok` ใน N นาทีถัดมา | **"คืนนั้นระบบเปิดเหตุจริง แต่ข้อความไม่เคยออกจากเครื่อง"** |
| `tg` ล้มเหลว และไม่มี `sms:*` ตามมา | fallback ไม่ทำงาน ไม่ใช่ Telegram ล่มอย่างเดียว |
| อาร์มอยู่ + `perm:revoked:<ที่โปรไฟล์ต้องใช้>` | เฝ้าอยู่โดยไม่มีสิทธิ์ที่จำเป็น |
| อาร์มอยู่ + `pwr:doze:enter` แต่ไม่มี `fgs:*` | ถูก doze ทั้งที่อ้างว่าเฝ้าอยู่ |
| ช่องว่างแถว `M` + `pwr:optimization:on` ก่อนหน้า | อธิบายการถูกฆ่าโดยไม่ต้องรอ `X` (ซึ่ง API 28 ให้ไม่ได้) |

**กฎสุดท้ายมีค่าเป็นพิเศษ** — เครื่องทดสอบเป็น API 28 แถว `X` เป็น no-op ตลอด
ชั้น D จึงเป็นทางเดียวที่เครื่องรุ่นนี้จะอธิบายการตายของตัวเองได้

## 9. ลำดับทำ

แบ่งเพื่อให้ **ส่วนที่เสี่ยงที่สุดขึ้นก่อนและวัดผลได้ ก่อนจะมีผู้ผลิตสิบตัว**

| เฟส | ทำอะไร | ทำไมลำดับนี้ |
|---|---|---|
| **D0** | ชนิดแถว `D` + enum + คิว + ถัง + แถว cap/drop + ขยาย `MAX_DIRECTORY_BYTES` + เทสต์ | ยังไม่มีผู้ผลิตสักตัว วัดพฤติกรรมถังกับงบดิสก์ได้ก่อนโดยไม่กระทบอะไร |
| **D1** | `tg` + `net` + `perm` | สามตัวนี้ตอบ "ทำไมไม่เตือนผม" ได้ครบวง ที่เหลือเป็นส่วนขยาย |
| **D2** | กฎขัดแย้งใน `BlackBoxReportBuilder` (§8) | ต้องมีข้อมูลจริงจาก D1 บนเครื่องก่อน ถึงจะรู้ว่ากฎไหนคุ้ม |
| **D3** | `pwr` `fgs` `gps` `sms` `mic` `therm` `boot` | ทีละตัว ตามที่ลูกค้าถามจริง |

**D0 + D1 คือขอบเขตของ C3** · D2 ต่อยอด C6 · D3 เปิดค้างไว้ตามความจำเป็น

## 10. เทสต์ที่ต้องมี

| เทสต์ | ปักอะไร |
|---|---|
| โดเมนเสียงดังกินสระกลางจนหมด `perm` ยังเขียนได้ | โควตายึดไม่ได้ทำงานจริง — **หัวใจของ §3** |
| ซ้ำ 40 ครั้งใน 3 นาที → 1 แถว `x40` | ยุบก่อนถึงถัง |
| ชนเพดาน → เงียบ → ชั่วโมงใหม่มีแถว `cap:<domain>:<n>` | กลไกเดียวกับแถว `T` |
| คิวเต็ม → ไม่ throw ไม่บล็อก และตัวเลขที่ตกไปถึงไฟล์ | บทเรียน `failureCount` |
| ชั่วโมงหมุนกลางคัน token คืนเต็ม | ขอบเขตของหน้าต่าง |
| แถว `D` ผ่าน `parse()` ได้ และ v1/v2 reader ไม่พังเมื่อเจอชนิดที่ไม่รู้จัก | ความเข้ากันได้ย้อนหลัง |
| งบดิสก์: 24 ชม. ชนเพดานเต็ม ไม่เกิน `MAX_FILE_BYTES` | §7 |

## 12. สามข้อที่เจ้าของเคาะแล้ว (2026-09-05)

### 12.1 ✅ บันทึก `/where` **และ** คำสั่งที่ถูกปฏิเสธ

วันนี้ [TelegramBotClient.kt:206](../MotorcycleAntiTheftSensor/app/src/main/java/com/example/motorcycleantitheftsensor/telegram/TelegramBotClient.kt)
ตอบคนนอกว่า "ไม่ได้รับอนุญาต" แล้วทิ้งคำสั่งไปเฉย ๆ ไม่บันทึกที่ไหนเลย

สองอย่างจึงมองไม่เห็นเลยตอนนี้ และทั้งคู่คือสิ่งที่เจ้าของต้องรู้:

- **คนนอกกำลังคลำหา** — การตอบกลับยังยืนยันให้เขารู้ด้วยว่าบอทมีจริงและยังทำงาน
  ใครลองมาสองร้อยครั้งเมื่อคืนก็ไม่มีร่องรอย
- **คนที่เข้าถึงแชทของเจ้าของได้แล้ว** ถาม `/where` ได้พิกัดรถไปโดยไม่ทิ้งอะไรไว้

```
D,...,1,ENTRY,7,,,,,,,0,,,tg:where:ok,0        ← 03:14 มีคนถามตำแหน่ง ตอบไปแล้ว
D,...,1,ENTRY,7,,,,,,,0,,,tg:cmd:denied x12,0  ← 03:15 คนนอกยิงมา 12 ครั้ง
```

**ไม่บันทึกว่าใครถาม** — กฎ §5 ห้าม chat id ลงไฟล์ และเจ้าของเป็นคนเดียวที่ควรถามอยู่แล้ว
"มีคนถาม ตอนนี้" คือข้อมูลทั้งหมดที่ต้องใช้ · `denied` อาจมีค่ากว่า `where` เสียอีก
เพราะมันคือสัญญาณว่ามีคนเจอบอทแล้ว

### 12.2 ✅ `perm:have:` ตอน start แทนการบันทึกทุกครั้งที่ได้สิทธิ์

ถ้าบันทึกเฉพาะตอนถูกถอน จะมีสองสถานการณ์ที่**หน้าตาเหมือนกันเป๊ะในไฟล์**:

| สถานการณ์จริง | ไฟล์เห็น |
|---|---|
| เคยมีสิทธิ์ แล้วถูกถอนก่อนไฟล์วันนี้เริ่ม | ไม่มีแถว `perm` |
| **ไม่เคยให้สิทธิ์นั้นเลยตั้งแต่ติดตั้ง** | ไม่มีแถว `perm` |

ทั้งคู่อ่านว่า "ตามรถไม่เจอ" แต่คนละสาเหตุคนละวิธีแก้

ถ้าบันทึกตอนได้สิทธิ์ด้วยก็แก้ได้ แต่ตอนตั้งค่าครั้งแรกผู้ใช้กดอนุญาต 5–8 อย่างในสองนาที
กินโควตา `perm` (4/ชม.) จนเต็มทันที **ทางที่เลือกคือเส้นฐานหนึ่งแถว:**

```
S,...,start,0
D,...,perm:have:loc.mic.notif,0     ← หนึ่งแถวต่อการเริ่มโปรเซสหนึ่งครั้ง
...
D,...,perm:revoked:location,0       ← 14:30 ถูกถอน
```

แถว `start` มีอยู่แล้วทุกครั้งที่โปรเซสเริ่ม (เมื่อวานเกิด 20 ครั้ง) จึงมีเส้นฐานให้อ่านตลอด
ถูกกว่าการบันทึกทุก grant และไม่เหลือความกำกวมข้างบน

### 12.3 ✅ หน้าต่างยุบอยู่ที่ 60 วินาที

5 นาทีประหยัดกว่า 5 เท่า (30 เหตุการณ์ → 2 แถว แทน ~10) แต่การยุบคือ**การพักไว้ใน RAM**

```
03:00  เน็ตหลุด      → รอหน้าต่างปิด
03:03  แอปถูกฆ่า     → แถวตายไปพร้อมโปรเซส ไม่เคยแตะดิสก์
03:05  (หน้าต่างที่จะปิด — ไม่มีวันมาถึง)
```

นี่คือเหตุผลเดียวกับที่ `BlackBoxWriter` เปิด-เขียน-ปิดทีละแถวไม่ยอมถือ buffer เลย
หน้าต่าง 5 นาทีเอา buffer กลับเข้ามาทางประตูหลัง ในนาทีที่เครื่องมีโอกาสถูกฆ่ามากที่สุด

60 วินาทีตรงจังหวะแถว `M` → เลวร้ายสุดเสียไม่ถึงหนึ่งนาที เท่ากับทุกอย่างอื่นในไฟล์
ส่วนที่ประหยัดได้คือ 550 ไบต์ในงบ 79 KB/วัน = **0.7%** ไม่ใช่ปัญหาที่ต้องแก้

**ผลต่อกลไก:** แถวแรกของแต่ละคีย์เขียนลงดิสก์ **ทันที** ไม่รอหน้าต่าง
หน้าต่างนับเฉพาะการเกิดซ้ำ แล้วสรุปเป็นแถว `x<n>` ตอนปิด — เหตุการณ์เดี่ยว ๆ
อย่าง `perm:revoked` จึงไม่เคยถูกหน่วง
